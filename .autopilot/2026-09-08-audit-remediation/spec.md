# Спецификация: исправления по аудиту aeecb2d

## Задача

Как владелец платформы, я получил независимый аудит, который честно показал:
в прод запускать нельзя — два блокера ломают деплой и мониторинг, а роль
аудитора может получить любой встречный с улицы. Я хочу план исправлений,
в котором ни одна подтверждённая находка не потерялась по дороге, критичное
чинится первым, а остальное лежит в приоритизированном бэклоге, а не в голове.

## Решение

Когда всё будет готово, у владельца будет:
1. Спека (этот файл) — каждая подтверждённая находка аудита с приёмкой.
2. Таски волнами: волна 1 — Blocker/Critical/High/CI, волны 2–3 — бэклог
   Medium/Low и DevOps-группа F по приоритету.
3. Зелёный CI и приёмка по каждой истории без запуска прод-контура.

Продуктовый код в прогоне спеки не меняется — только `.autopilot/`-артефакты.

## Решения по реализации

1. Redis — обязательная прод-зависимость с health-check в readiness: иначе два инстанса молча удваивают лимиты и теряют события. Почему так: in-memory fallback чинит локалку и ломает прод.
2. Карта роутов для метрик строится после подключения всех роутеров; значения меток экранируются по exposition-формату; для несопоставленных путей — одна bounded-метка. Почему так: иначе кардинальность растёт от входных данных.
3. Привилегированные роли — через явный allowlist саморегистрации (только непривилегированные слаги); выдача — только администратором; отзыв — миграцией данных. Почему так: запрет по списку «кроме staff» уже пропустил auditor один раз.
4. SSE — двухшаговый контракт: выпуск короткоживущего одноразового ticket по авторизованному POST, стрим по ticket в query; токен в URL запрещён; query стрима исключён из access-лога. Почему так: EventSource не умеет в заголовки, а логи читают люди.
5. Лимит реестров классифицирует запрос по валидированному пользователю, а не по наличию заголовка. Почему так: заголовок подделывается одной строкой.
6. Ротация refresh — одним атомарным UPDATE с условием «ещё не отозван»; повтор — 401 с отзывом семьи. Почему так: check-then-act в двух запросах проигрывает гонку всегда.
7. LLM — за очередь с коротким таймаутом синхронного пути и мгновенным fallback; пользовательский контент документов изолируется разделителями, ответ парсится строгим шаблоном. Почему так: 60 секунд удержания соединения — это даун всей платформы при дауне провайдера.
8. Семантика — через обучаемую embedding-модель с переиндексацией, а не хеш-корзины токенов. Почему так: хеш не знает синонимов, а «сопоставление по смыслам» — заявленная функция.
9. Статусы жизненных циклов — CHECK-ограничения в БД плюс пагинация списков и batched-загрузка связей. Почему так: свободные строки и полные выборки гниют тихо и взрываются на росте.
10. CI ловит то, что ломалось: линт тестов, сборка образов, smoke готовности зависимостей. Почему так: каждый из блокеров проходил мимо текущего CI.

|---|---|---|---|
| `auth` | регистрация, refresh-ротация, троттлинг входа | `POST /auth/*` | хранилище попыток, семейство токенов |

| `frontend-auth` | токены в браузере, offline-очередь | очередь без секретов, инъекция токена в момент отправки | сессия NextAuth |

| `infra-backup` | бэкап перед миграциями | fail-closed гейт «бэкап готов → мигрируем» | lock-идентификаторы |

Швы для тестов — публичная HTTP-граница API плюс существующие гейты (`pytest`, `npm test`, линт, сборки). Идеал — один шов: поведение проверяется через HTTP, Phase 5 тестирует только здесь. Новые регрессионные тесты идут через тот же шов, которым пользуется прод.
