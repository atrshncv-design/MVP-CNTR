# 01 — Redis как обязательная прод-зависимость

**Требования:** R03i (истории 3, 4)
**Blocked by:** —
**Зона:** `backend/deps`, `backend/health`, `infra/compose`
**Волна:** 1
**Status:** ready

## Что должно заработать

Rate-limit реестров и троттлинг входа работают одинаково на любом числе
реплик: клиентская библиотека Redis входит в зависимости образа, прод без
доступного Redis не стартует молча, а падает с понятной ошибкой; readiness
отражает состояние Redis.

## Из брифа, дословно

> составь спеку и тикеты для внесения правок
> «Всё + приоритеты»: спека покрывает все подтверждённые находки; таски — на Blocker/Critical/High/CI (Дополнения 2026-09-08)

## Разделы спецификации

Истории 3–4, Решения §1, §10, Границы `auth`, `registry`, `infra-observe`.

## Критерии приёмки

- [ ] Клиент Redis есть в зависимостях образа; импорт в прод-образе успешен
- [ ] Без доступного Redis прод-контур — fail-fast со внятной ошибкой, in-memory fallback в проде запрещён
- [ ] Readiness отдаёт 503 при недоступном Redis; алерт уходит
- [ ] Лимит 120 анонимных запросов держится суммарно при двух репликах, а не на каждой
- [ ] SSE-событие, опубликованное на одной реплике, доходит до клиента другой
- [ ] Тест на шве HTTP покрывает лимит и кросс-реплику доставку
