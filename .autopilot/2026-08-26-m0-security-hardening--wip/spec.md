# Спецификация: M0 — гигиена и безопасность платформы (закрытие гейта G1)

## Задача

Я отвечаю перед государственным заказчиком за платформу с персональными данными и конфиденциальными документами НИОКР. Независимый аудит нашёл дыры: можно обойти модерацию при вступлении в проект и увидеть чужие закрытые документы; маршруты кабинетов открыты всем ролям; прод-сборка без одной переменной отправляет данные пользователей на их localhost; при аварии я потеряю все транзакции между бэкапами, потому что их не то что не восстанавливают — их никто не делает по расписанию; о падении сервиса в выходные никто не узнает. Деплой не умеет откатываться, Grafana торчит наружу с паролем по умолчанию. Мне нужен контур, который не стыдно показать заказчику в декабре: безопасный, переживающий отказы с потерей не больше минут данных, и сообщающий мне о проблемах в Telegram. Срок закрытия этого этапа — до 30 сентября 2026 (гейт G1 плана).

## Решение

К концу прогона владелец получает:

1. **Закрытые дыры доступа**: вступление в проект невозможно провести мимо модерации; маршруты кабинетов закрыты матрицей ролей, работающей по принципу «запрещено по умолчанию»; единая точка формирования адреса API убирает localhost-fallback из прода.
2. **Безопасные сессии и загрузки**: смена пароля убивает все сессии, есть logout; загрузка документов этапа ограничена по размеру на любом пути до приложения.
3. **Надёжность данных**: бэкапы делаются ежедневно сами; WAL архивируется непрерывно (потеря ≤ 5 мин); слот репликации не может переполнить диск; есть offsite-копия; восстановление на чистом контуре отрепетировано и задокументировано.
4. **Наблюдаемость и управляемость**: скрипт-алертер шлёт владельцу в Telegram о падении readiness, недоступности реплики, устаревании бэкапа, переполнении диска; deploy.sh сам проверяет здоровье после выката и откатывается на предыдущие образы при неудаче; Grafana доступна только через SSH-туннель.
5. **Конвейер качества**: GitHub Actions гоняет тесты/линтеры/типы обоих приложений на каждый push.
6. **Документы для заказчика**: одностраничные техтребования к серверу и оценка стека на импортозамещение.

## Решения по реализации

- **Атрибуция рефералки (R01)** — сервер генерирует ссылку с подписанным (HMAC) параметром либо хранит автора ссылки у себя в момент создания; поле `shared_by` из тела запроса игнорируется полностью. Почему: любой клиент-controlled ID — перебираемый serial.
- **Матрица ролей (R02)** — явные записи для всех существующих маршрутов `/dashboard/*` + правило «маршрут без записи → запрет». Почему: fail-open уже дал дыру; новые маршруты должны появляться в матрице осознанно, тест не даст забыть.
- **Единый URL-API (R03)** — браузер ходит всегда по относительному `/api/v1` того же origin (rewrites), SSR — внутреннему адресу из env; `NEXT_PUBLIC_API_URL` становится опциональным оверрайдом; его отсутствие в prod больше не даёт fallback. Почему: один origin упрощает CSP (`connect-src 'self'`) и исключает mixed-content.
- **CI (R04)** — GitHub Actions, сервис-контейнер БД на образе с pgvector (тесты создают свою БД и гоняют alembic); mypy доводится до зелёного в рамках тикетов этого прогона, отдельные послабления не вводятся. Почему: «strict объявлен, но не доказан» — найденная аудитом нечестность.
- **Бэкапы (R07)** — ежедневный запуск существующего backup.sh таймером внутри прод-стека; возраст последнего успеха пишется файлом-маркером, который читает и алертер, и метрика приложения. Почему: переиспользуем проверенный скрипт, не изобретаем второй путь бэкапа.
- **WAL/PITR (R08)** — `archive_command` на отдельный том + `archive_timeout=60s`; репетиция = чистый контейнер PostgreSQL, восстановление base+WAL до момента между двумя контрольными вставками, сверка строки. Почему: цель «ноль потерь» на одном хосте достижима только так; без репетиции это надежда, а не свойство.
- **Offsite (R10)** — необязательный шаг копирования архива через rclone-таргет из env; таргет не настроен → предупреждение алертера и строка в требованиях к серверу. Почему: выбор хранилища зависит от сервера заказчика, которого ещё нет; затычка конкретного облака была бы выдумкой.
- **Алертер (R11)** — маленький скрипт по расписанию внутри прод-стека (тот же механизм, что бэкапы): опрашивает readiness, слот/лаг реплики, маркер бэкапа, df, состояние offsite; дедупликация — активная авария не спамит, сообщение о восстановлении отправляется. Grafana остаётся визуализацией. Почему: надёжнее и проще, чем связка provisioning-файлов Grafana, и тестируется юнит-тестом без Grafana.
- **Rollback (R12)** — теги образов = git SHA; deploy.sh ждёт healthy (таймаут), при провале перевкатывает предыдущие теги и выходит с ошибкой. Почему: «печатать ✅ при упавшей миграции» хуже, чем ничего.
- **Grafana (R13)** — порт хоста убран, доступ по SSH-туннелю; строгий режим секретов распространяется на пароль Grafana. Почему: панель с внутренней телеметрией не должна быть частью атакующей поверхности B2G.
- **Пул БД (R14)** — снижение дефолтов пула до согласования с `max_connections=100` при двух репликах + guard-тест формулы. Почему: дешевле, чем pgbouncer, и достаточно для пилота; pgbouncer — тема P2.
- **Logout/ревок (R15)** — logout ревокает текущий refresh; смена пароля — все refresh пользователя; access доживает до истечения (≤60 мин), это принято и документируется. Почему: без stateful-блоклиста access инвалидируется деактивацией пользователя, но не «выходом»; компромисс честнее фальшивых обещаний.
- **Лимиты тела (R16)** — тот же лимитированный читатель, что в project-files/news-media; middleware при отсутствии Content-Length читает поток до лимита+1 и отвечает 413. Почему: закрывает и прямой путь, и chunked-bypass одинаковым механизмом.
- **Ветка и коммиты** — работа на ветке `autopilot/m0-security-hardening`, созданной от актуального `main`; push в origin после каждого таска; merge в main только после приёмки. Почему: правило репозитория и push-контракт AGENTS.md.
- **Закрытие пунктов реестра** — таск, закрывающий пункт BACKLOG.md, обязан в том же коммите перевести строку реестра в `done` и вписать хеш. Почему: реестр — источник истины по составу прогона; расхождение кода и реестра = несданный пункт.

## Границы и швы

Прогон меняет существующие модули; новых подсистем две (алертер, CI-workflow) — обе изолированные.

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `backend/auth-sessions` | правила вступления в проект, жизненный цикл refresh-токенов | существующие эндпоинты membership/auth с прежними контрактами (минус доверие `shared_by`, плюс logout) | механику HMAC-ссылок и ревокаций |
| `backend/uploads` | лимитирование чтения загружаемых тел | общий лимитированный читатель (уже существует) для всех точек загрузки | детали потокового чтения/дропа |
| `frontend/access` | источник адреса API + матрица ролей маршрутов | единый модуль экспорта базового URL; карта `роль → маршруты` | способ разрешения URL (rewrites/env) |
| `infra/data-safety` | бэкапы, WAL, слот репликации, offsite | команды backup/restore/rehearse-pitr; маркер свежести бэкапа | расположение томов и параметры архивации |
| `infra/edge` | деплой, откаты, публикация портов, алертинг | deploy.sh с health-gate; алертер с env-конфигурацией | логику дедупликации аварий |
| `ci` | workflow обоих приложений | зелёный статус на push | — |
| `docs/customer` | техтребования к серверу, импортозамещение | два документа в `docs/` | — |

Швы для тестов: **существующий pytest-сьют бэкенда**, **существующий node --test фронтенда**; добавляются ровно два — регрессионный тест покрытия матрицы маршрутов (frontend) и guard-тест формулы пула (backend). Репетиция PITR — одноразовый исполняемый сценарий с записью результата в отчёт прогона.
