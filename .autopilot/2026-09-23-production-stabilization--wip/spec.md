# Спецификация: стабилизация production «Технозрелости» по итогам аудита 2026-09-21

## Задача

Платформа прошла доказательный production-аудит: gate — GO WITH CONDITIONS, 30 findings (2 high, 9 medium, 19 low), 4 блокирующих условия C1–C4. От лица владельца: нельзя эксплуатировать и масштабировать контур, пока backup никуда не доставляется, restore не доказан, ролевые сценарии не проверены, а локальные гейты не воспроизводятся. При этом живой production трогать нельзя без отдельного разрешения на каждое действие.

## Решение

Когда всё готово: стабилизационная ветка содержит атомарные исправления с regression-тестами и доказательствами; гейты backend/frontend воспроизводятся локально и зелёные; offsite-backup и restore-подготовка доведены до `READY FOR APPROVAL` с change plan'ами; ролевая матрица покрыта локальными тестами, runtime-часть честно `BLOCKED`; спорные архитектурные вопросы зафиксированы ADR; traceability `finding → ticket → commit → test → evidence` и acceptance-отчёт позволяют вынести чистый `GO`, `GO WITH CONDITIONS` или `NO-GO`. Production при этом не изменён ни разу.

## Уточнение AI и исполнения (R33–R35, 2026-09-24)

Под AI-функциями в цели владельца понимаются два пользовательских ассистента: по документам и по реестрам. Таски T23/T24 проверяют их сквозные локальные пути отдельно от общих AI-ограждений T08/T14. Новый ключ для другой модели владелец добавит после текущих правок; до этого live provider проверка остаётся `BLOCKED`, а код, безопасные fallback, retrieval и синтетические офлайн-тесты выполняются без ключа. Значения ключей не запрашивать и не записывать.

Исполнитель продуктового кода теперь запускается в Codex с моделью `gpt-6-luna`, reasoning `high`, в отдельном контексте на каждый таск. Оркестратор сохраняет spec/manifest/state/dashboard, ревью, регрессию, commit и push. Инструкции про OpenCode в ранних разделах и историческом brief относятся только к уже завершённым попыткам; R35 — позднейшее указание владельца.

T02 выявил D01: тестовая БД восстановлена, но 15 существующих тестов не принимают новый keyword `session_id` в mocks. T22 отдельно восстанавливает тестовый контракт без изменения приложения, после чего T02 gate повторяется. Это изменение плана вызвано проверенным результатом T02, не снимает R20/R21 и не считается закрытием CODE-03 до зелёного полного suite.

## Решения по реализации

Ярус T3, 21 тикет (больше лимита 16 — обоснование: атомарность «один finding — один тикет» прямо заказана владельцем (G03); волны в основном последовательные, параллельность только по непересекающимся зонам; цена границы минимизирована жёстким контрактом исполнителя и готовыми швами).

1. База — стабилизационная ветка от аудит-коммита: в ней уже лежат immutable evidence, findings и методологический ADR; traceability работает внутри ветки без второго checkout. Почему так: требование G01/G02 пользователя.
2. Сначала окружение и честный baseline (Волна 0), потом код. Почему: чинить findings на невоспроизводимых гейтах — строить на песке (CODE-03/CODE-06 прямо об этом).
3. Каждый finding чинится по правилу 11 шагов из брифа: evidence → repro → failing test → fix → focused → regression → ревью → docs → commit → push. Почему: только так закрытие считается доказанным, а не заявленным.
4. Волны идут строго по порядку G04: гейты → quick wins T05–T12 → regression → T13–T18 → change plans → runtime после аккаунтов → приёмка. Почему: решение пользователя, снимающее спор о приоритетах.
5. Инфраструктурное (SEC-01, DB-04, DB-05, OPS-02/03) готовится как код + тесты + runbook + change plan + rollback + stop conditions, применяется только после отдельного разрешения. C1/C2 до разрешения — `READY FOR APPROVAL`. Почему: production жив и single-node; цена ошибки — простой и потеря данных.
6. AI-ограничения (полный контур: injection resistance, tenant isolation, grounding, citations, structured-output validation, timeout, retry policy, concurrency limit, per-route rate limit, quota/budget guard, circuit breaker, provider failure fallback, persistent метрики, staleness monitoring, chunking с overlap, PII-контроль промптов) — кодом; live eval — не дороже 200 вызовов, только ГОСТы и синтетика, ПДн под запретом. Allowlist будущих полей: модерированное название, отрасль, тематика, УГТ, технологии, требуемые компетенции, обезличенное описание. Почему: spend-поверхность без крышки — финансовый риск, ПДн — правовой.
7. Волна 4 — только ADR с вариантами, рисками, стоимостью, миграцией и явно требуемым решением. RLS, soft delete, MFA, blocklist, HA, zero-downtime, реестры, анкеты, P2 — молча не реализуются. Почему: это бизнес-политика, а не техника.
8. Тестовые аккаунты не создаются самостоятельно; runtime-матрица до их выдачи — `BLOCKED`. Почему: запрет брифа и здравый смысл.
9. Оркестратор пишет spec/тикеты, ревьюит diff, гоняет тесты, коммитит и пушит; исполнитель в новой сессии правит только разрешённые файлы и не коммитит; выбранная модель не заменяется без разрешения. Почему: контракт G09, иначе статусы и артефакты расползутся.

## Правила миграций и изменений (R27 детали)

- Схема — только Alembic, с upgrade и downgrade; SQL — только ORM или безопасно параметризованные конструкции.
- Миграция сначала проверяется локально/staging; production migration — только с отдельного разрешения.
- Публичные API, схему БД и бизнес-поведение не менять без явной необходимости и документированной миграции.
- Не объединять несвязанные изменения в один тикет или commit; массового рефакторинга «заодно» нет.

## Запреты production и стоп-триггеры (R28 детали)

Без отдельного разрешения запрещены: изменение production; создание/удаление реальных данных; DDL и миграции; рестарт сервисов; deploy; смена secrets, DNS, firewall, TLS; restore на production; fuzzing; нагрузочные тесты; чтение и вывод `.env`, private keys, credential stores; вывод токенов, cookies, email, телефонов и содержимого пользовательских проектов. Разрешены только пассивные read-only проверки и редкие smoke-запросы. Немедленная остановка при: росте 5xx; unhealthy; заметном росте latency; неожиданной записи; появлении чувствительных данных.

## C1 — детали (R17)

`BACKUP_OFFSITE_REMOTE` настраивается через штатный secret/configuration mechanism; значения секретов не попадают в Git, логи и отчёты. Требуются: свежий успешный marker; retention-политика и контроль устаревания; наблюдаемый alert при сбое доставки.

## C2 — детали (R18)

Только staging/изоляция, production не затрагивается. Фиксируются дата и идентификатор backup; схема и данные восстанавливаются в изолированную БД; выполняются integrity/smoke checks; измеряется фактический RTO; оценивается достижимый RPO; пишется rehearsal-отчёт.
