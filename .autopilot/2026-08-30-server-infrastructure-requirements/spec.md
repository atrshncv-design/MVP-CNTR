# Спецификация: требования к серверной инфраструктуре «Технозрелости»

## 1. Задача

Подготовить проверяемый отчёт по серверному оборудованию для существующей платформы,
не меняя код и конфигурацию. Отчёт должен связать каждую рекомендацию с фактическим
компонентом проекта, измерением либо явно обозначенным сценарием и завершиться практичной
закупочной спецификацией.

## 2. Зафиксированные входные данные

| Параметр | Значение | Статус |
|---|---:|---|
| Одновременно вошедшие пользователи | до 10 000 | задано пользователем |
| HTTP-нагрузка | 300–500 RPS | задано пользователем |
| Облачные LLM-запросы | 1 000/час | задано пользователем |
| Прирост файлов | 1 ГБ/день | задано пользователем |
| Основная схема | два сервера | задано пользователем |
| Бюджетное ожидание | менее 1 млн ₽ | задано пользователем |
| Доступность | 99,9% | задано пользователем |
| RPO / RTO | 5 минут / 1 час | задано пользователем |
| Новое или refurbished | не определено | placeholder G10; рассчитать оба |

Для параметров, которых нет в проекте и ответах, отчёт использует отдельные сценарные
допущения. Они не подменяются «средними по рынку» без явной маркировки.

Блокирующий брифинг завершён до расчёта. Каждый вопрос сопровождался объяснением влияния
на CPU/RAM/DB/network/storage/HA и вариантами диапазонов. Ответы зафиксировали concurrency,
RPS, LLM rate/location, file growth, SLA/RPO/RTO, число серверов и бюджет. Неопределённый
тип закупки закрыт двумя расчётными ветками, а не новым вопросом.

## 3. Доказательная база

Анализ охватывает канонические frontend/backend, ORM и всю цепочку миграций, Docker и
Compose, nginx, PostgreSQL/Redis/MinIO/ClamAV, backup/PITR, monitoring, CI, скрипты
нагрузочного тестирования, отчёты прошлых прогонов, Autopilot-спеки и тикеты, документацию
и переменные окружения. Архивные, плановые и stub-данные отделяются от текущего кода и
измерений.

Каждый технический вывод в отчёте содержит ссылку `путь:строка`. Характеристики конкретного
оборудования подтверждаются официальной страницей или datasheet производителя. Цена
содержит дату, регион, валюту, URL и статус: текущая цена, цена без подтверждённого наличия
или оценка. Оценка не выдаётся за коммерческое предложение.

## 4. Фактическая архитектура

Отчёт восстанавливает:

- назначение B2B/B2G-платформы, девять ролей и ключевые пользовательские сценарии:
  auth, оценка УГТ, проекты/участники, документы, повышение УГТ, реестры, новости,
  notifications/SSE и AI/RAG;
- состав frontend/backend, языки, frameworks и runtime с версиями из config/lock-файлов;
- browser → nginx → Next.js/FastAPI;
- две FastAPI-реплики, PostgreSQL Primary/Replica, Redis, MinIO, ClamAV;
- pgvector 1536, CPU hashing embeddings и внешний OpenAI-compatible LLM;
- SSE, scheduler новостей, backup timer, WAL offsite, alerter, Prometheus/Grafana;
- отсутствие task queue, OCR, speech, reranker, локального neural inference и Kubernetes;
- single-host Compose как текущую production-топологию и её SPOF.

Отдельно перечисляются все найденные способы развёртывания и внешние интеграции, включая
LLM API, rclone offsite и Telegram alerts. Перед архитектурой отчёт содержит три явных
списка: подтверждено проектом; обоснованно выведено; отсутствует и требует уточнения.

Компоненты классифицируются по постоянной, пиковой, CPU-, RAM-, disk- и network-нагрузке,
необходимости GPU, отдельного узла и допустимости совместного размещения на MVP.

## 5. Методика расчёта

### 5.1 CPU

За базу берётся измеренный локальный предел: около 55–61 RPS при загрузке backend CPU около
0,89 ядра. Производительность нормируется как приблизительно 67 RPS/ядро, после чего
применяется коэффициент 1,5–2,5 на TLS, auth, логирование, неидеальное масштабирование,
фоновые процессы и отказ одного узла.

Формула:

`CPU_api = RPS × (0,89 / 60) × K`.

Отдельно добавляются ядра PostgreSQL, ClamAV, MinIO/Redis/nginx/monitoring и ОС. SMT-потоки
не считаются физическими ядрами для гарантии.

### 5.2 RAM

RAM складывается по сервисам и проверяется двумя способами:

1. сумма рабочих наборов API, PostgreSQL, ClamAV, Redis, MinIO, monitoring и ОС;
2. failover-сценарий, когда один сервер временно несёт все роли.

Нормальная загрузка RAM не выше 70–75%. PostgreSQL получает достаточный page cache; RAM и
VRAM учитываются раздельно. Для облачной LLM VRAM равна нулю.

### 5.3 Хранилище

Файлы: `1 ГиБ/день × 365 × годы`, затем +30% на версии/метаданные и деление на 0,8 для 20%
свободного пространства. Отдельно прибавляются PostgreSQL, индексы, WAL, temporary area,
логи, monitoring и backup. Указываются raw и usable после RAID.

Основные данные используют enterprise TLC SSD с PLP. RAID защищает от отказа диска, но не
считается backup. QLC и consumer SSD без документированной PLP не рекомендуются для Primary.

### 5.4 Сеть

`Mbps = RPS × средний payload KiB × 8 / 1024`.

Публичный канал считается для payload 50/100/250 KiB. Внутренняя сеть отдельно учитывает
WAL, object replication, backup, ClamAV и failover. Для двух узлов базово рассматривается
10GbE; 25GbE допускается только при доказанной необходимости.

### 5.5 LLM

`1 000/час = 0,278 запроса/с`. Конкурентность считается как RPS × latency: при 5/10/30/60 с
это около 1,4/2,8/8,3/16,7 запросов. Для текущего облачного варианта требуется очередь или
semaphore около 20–25 запросов, но не GPU.

## 6. Сценарии нагрузки

Отчёт содержит четыре самостоятельных сценария с зарегистрированными пользователями,
DAU/MAU, concurrency, RPS, background jobs, DB/files, приростом, трафиком, latency,
ресурсными пределами и коэффициентом запаса:

- A: MVP, один сервер допустим, короткий простой допустим;
- B: пилот, два узла, до 300 RPS и базовое резервирование;
- C: production, 10 000 concurrent, 300–500 RPS, 1 000 LLM/час;
- D: рост 2–3 года, накопление документов, RAG и фоновых задач.

Не заданные пользователем cardinality помечаются как допущения. Сценарий C дополнительно
разделяется на normal two-node и single-node degraded/failover режим.

Количество фоновых задач задаётся как фактическая частота scheduler/backup/WAL/alerter и
сценарное число upload, notification fan-out, RAG ingestion и LLM jobs. Для каждой цифры
указывается источник либо формула.

## 7. Ресурсы по компонентам

Для backend, frontend/nginx, Primary/Replica, Redis/SSE, scheduler/workers, pgvector/RAG,
ClamAV/document processing, MinIO, monitoring/logs, backup и CI/staging указываются:

- физические ядра и значение частоты;
- RAM, тип памяти и запас;
- VRAM;
- storage class, usable volume, IOPS и throughput;
- network bandwidth;
- число экземпляров;
- способ горизонтального масштабирования и текущие ограничения кода.

Для RAM указывается тип и фактическая/рекомендуемая скорость. Генерация текущих CPU-hashing
embeddings и возможных neural embeddings получает отдельный ресурсный расчёт.

Отсутствующие отдельные сервисы (полнотекстовый движок, task queue, local embeddings,
local LLM) не получают выдуманный сервер: отчёт объясняет, какая существующая часть выполняет
их функцию и при каком изменении понадобится выделение.

## 8. AI-варианты

Сравниваются три варианта:

1. текущий: LLM через внешний API, CPU hashing embeddings, GPU не нужен;
2. локальные neural embeddings/OCR/reranker, LLM через API;
3. локальная LLM и весь AI-контур.

Для вариантов 2–3 приводятся классы моделей, FP16/BF16/INT8/INT4, VRAM, примерная скорость,
параллельность, PCIe, multi-GPU, питание, охлаждение и ограничения consumer GPU. Они являются
условными ветками развития, а не рекомендацией купить GPU сейчас.

Для текущего API отчёт проверяет `max_tokens`, объём передаваемого RAG-контекста и наличие
model context window; отсутствующее значение не придумывается. Для локальных вариантов
скорость выражается в tokens/s и concurrent sequences, GPU performance — для конкретного
класса модели/quantization. Экономика сравнивает CAPEX, электроэнергию и cloud token-cost;
при отсутствии тарифов даётся формула break-even и перечень требуемых входных данных.

## 9. Конфигурации оборудования

Для A/B/C/D приводятся минимальная, рекомендуемая и расширенная конфигурации. Основная
практичная ветка ограничена одним-тремя серверами; Kubernetes, SAN и GPU-кластер не
предлагаются.

Основной кандидат новой двухузловой платформы проверяется вокруг AMD EPYC 4004/4005,
ECC DDR5 UDIMM, BMC/IPMI, 128 ГБ на узел, enterprise SSD с PLP и 10GbE. Сравниваются Intel
Xeon E-2400 и refurbished Dell/HPE. Для каждого компонента проверяются socket, TDP, memory
channels/slots/max, PCIe, NIC, form factor, cooling и точные артикулы.

Каждая конфигурация содержит:

- CPU: architecture, model, sockets, cores/threads, base/boost, TDP и причина выбора;
- RAM: volume, DDR, ECC/non-ECC, UDIMM/RDIMM, MT/s, модули, заполнение каналов, свободные
  slots и platform maximum; отдельно обосновываются ECC и допустимость non-ECC;
- motherboard: server class, socket, chipset, channels/slots, PCIe generation/lanes,
  BMC/IPMI, NICs, expansion и подтверждённая совместимость;
- storage по OS/DB/indexes/temp/files/logs/backup: interface, TLC/QLC, enterprise/consumer,
  capacity/count, TBW/DWPD, PLP, RAID, raw/usable, free-space target и hot-swap;
- GPU-ветки: model, VRAM и memory type, TDP, slots, cooling, count, context/model limits и
  expected performance;
- network: interfaces, storage/backup separation, switch class/ports, public bandwidth и
  monthly traffic;
- chassis/power: tower/rack и U, bays, airflow, PSU watts/redundancy, idle/normal/peak watts,
  BTU/h, UPS VA/W/runtime и требования к помещению.

Для ключевых компонентов даются альтернативы разных производителей только после проверки
datasheet/QVL; неподтверждённая позиция остаётся классом требования, а не совместимой моделью.

Бюджетная рекомендация обязана прямо сказать: два 16-ядерных узла рассчитаны на совместные
300–500 RPS, но после отказа одного узла гарантируют деградированный режим порядка 250–300
RPS до восстановления. Для полных 500 RPS на одном узле требуется класс 24–32 физических
ядер на каждый сервер, который показывается отдельно как дорогой запас.

## 10. Размещение

Сравниваются один физический сервер, два/три сервера, dedicated, cloud, hybrid и отдельный
AI-host. Основная схема:

- узел 1: Primary и часть stateless-сервисов;
- узел 2: Replica, вторая часть stateless-сервисов и тёплый резерв;
- object data реплицируется явно, backup хранится вне обоих узлов;
- переключение БД при двух voting nodes ручное либо с внешним witness, чтобы избежать
  split-brain;
- cloud LLM остаётся внешним.

Каждый вариант размещения оценивается по одной матрице: performance, CAPEX, OPEX,
reliability, scalability, maintenance complexity, security, redundancy, recovery time и SPOF.

Отдельно показываются простая MVP-схема на одном сервере и корректная production-схема на
двух узлах с внешним backup/witness. Ни RAID, ни dual PSU, ни VM не называются заменой
второму узлу.

## 11. Backup и отказоустойчивость

Отчёт определяет критичные PostgreSQL/MinIO/секреты/конфигурацию, RPO/RTO, full/base backup,
WAL, retention, offsite encryption, restore drills и восстановление после отказа диска,
сервера и площадки. Правило 3-2-1 рассматривается отдельно от RAID.

Указываются интервалы full/base, WAL/incremental и offsite, сроки хранения, raw/usable backup
capacity, окно копирования и restore drill. Неизвестные compression ratio/change rate даются
диапазонами.

Цель 99,9% допускает около 43,8 минуты простоя в месяц; RTO 1 час является DR-пределом, но
сам по себе не гарантирует 99,9%. Для routine failover целевое переключение должно быть
5–15 минут, что требует проверки.

## 12. Экспериментальная проверка

Безопасные измерения включают текущий `docker ps/stats/system df`, статическую проверку,
существующие отчёты и короткий smoke при наличии полного контура. Опасный или длительный
load test без отдельного согласия не выполняется.

Отчёт фиксирует, какие сервисы не были запущены, что помешало измерить полный idle/API/file/
background profile, что осталось неизвестным и как пересчитать CPU/RAM/disk/network после
benchmark. Сборка и запуск выполняются только при безопасно доступных зависимостях.

До закупки требуется production-like benchmark: 300 и 500 RPS, 10 000 SSE/TLS connections,
реалистичные auth/read/write/file/LLM профили, p95 read ≤500 ms, p95 write ≤1 s, success ≥99%,
replica lag, one-node failure и полный restore. Непроверенные показатели остаются
условными, а не объявляются гарантией.

## 13. Стоимость и модернизация

Показываются новый и refurbished BOM. Неподтверждённые российские цены маркируются как
оценки; итоговая закупка требует коммерческих предложений с точными P/N, наличием и
гарантией. Целевой бюджет основной ветки — менее 1 млн ₽.

Стоимость разбивается на platform/CPU, RAM, накопители, GPU отдельно, NIC/switch, UPS,
backup storage, chassis/PSU, электроэнергию и OPEX; называются самые дорогие позиции.
Для каждого варианта размещения приводятся стартовые и регулярные расходы.

Сразу правильно выбираются платформа, BMC, ECC, chassis airflow, PSU, PCIe, DIMM slots,
drive bays и 10GbE. Позже можно наращивать SSD, backup capacity и часть RAM, если остаются
слоты; замена всех четырёх DIMM считается отдельным ограничением.

Порядок модернизации: измерения и storage monitoring; RAM/SSD; API replicas и DB pooling;
третий witness/узел; локальный AI/GPU только после отдельного economic/performance benchmark.

## 14. Формат итогового отчёта

Итог содержит 15 запрошенных разделов в заданном порядке и финальную закупочную таблицу с
колонками: компонент, минимальное требование, рекомендуемая модель/класс, количество,
допустимые аналоги, обоснование.

## 15. Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| `evidence` | факты из репозитория и измерений | матрица `вывод → путь:строка` | архивные/stub противоречия |
| `capacity` | формулы и сценарии A–D | CPU/RAM/storage/network budget | сценарные допущения |
| `hardware` | проверенные модели и совместимость | BOM и официальные URL | неподтверждённые цены |
| `operations` | topology, HA, backup, DR | MVP/production схемы и RPO/RTO | runbook details |
| `report` | единый документ | 15 разделов + закупочная таблица | рабочие заметки |

Главный проверочный шов — итоговый отчёт: независимый reviewer сверяет его с брифом и
репозиторием, не с этой спецификацией.

## 16. Вне рамок

- Изменение приложения, Compose, nginx, БД или CI исключено требованием R06.
- Опасный/длительный load test исключён R54 без отдельного согласия.
- Покупка, публикация, deploy и запрос коммерческого предложения не выполняются.
- Точная цена без доступного публичного предложения не выдумывается; указывается диапазон
  и необходимость КП.
