# Промпт для дешёвой модели: продуктовые паттерны i.moscow

Ты работаешь над платформой «Технозрелость». После завершения основного Friday Release Candidate внедри продуктовые и интерфейсные паттерны, выделенные из i.moscow. Не создавай клон портала и не заменяй бренд платформы.

## До любых изменений прочитай полностью

1. `AGENTS.md`, `CLAUDE.md`, `Plan.md`, `Status.md`.
2. `.scratch/friday-release-candidate/spec.md` и все тикеты `.scratch/friday-release-candidate/issues/` с их текущими статусами.
3. `.scratch/imoscow-product-patterns/spec.md` и все тикеты `.scratch/imoscow-product-patterns/issues/`.
4. `docs/agents/domain.md` и `docs/agents/issue-tracker.md`.
5. Актуальный frontend/backend-код, тесты, миграции и дизайн-токены.

При конфликте: AGENTS/безопасность → базовая Friday-спека → i.moscow-спека → отдельный тикет.

## Запрет параллельного конфликта

Не начинай, пока другая модель меняет те же frontend/backend-ветки по Friday Release Candidate. Сначала дождись её завершения, зафиксируй commit SHA и выполни baseline. Это следующий последовательный этап.

## Целевой результат

Платформа воспринимается как единое окно развития проекта: подтверждённый и предварительный УГТ разделены; видны следующая цель, прогресс, блокеры, ответственный, статус и одно основное действие; результат оценки ведёт в проект; публичная карточка доказательна; фильтры реестра передаются ссылкой.

i.moscow — референс карточной композиции, ясной иерархии, спокойной плотности, коротких статусов и навигации по задачам. Его актуальная айдентика изумрудная, но **изумрудный не переносится в бренд «Технозрелости»**. Сохрани синий технологический дизайн-код и три темы: светлую, тёмную, удмуртскую чёрно-красно-белую.

## Порядок работы

1. Работай только в отдельном git worktree и ветке `codex/*`; не меняй `main` напрямую.
2. Сними baseline: SHA, миграции, frontend lint/typecheck/build/tests, backend lint/tests, Docker и существующий E2E.
3. Красный baseline не маскируй: зафиксируй и отдели существующий дефект от своей работы.
4. Реализуй frontier зависимостей. Один тикет = один свежий агентный контекст = один атомарный commit.
5. Статус тикета: `in-progress` перед началом, `done` только после приёмки.
6. После каждого успеха обновляй `Status.md` и `PROGRESS.md`.
7. Каждый commit отправляй в `origin`.
8. Тикет 08 — P1; не начинай его до зелёного P0 release gate.

Frontier: 01 → (02, 03, 04; параллельно только при раздельных файлах) → 05 → 06 → 07 → после отдельного решения 08. Не запускай параллельно агентов, меняющих общие API, компоненты, токены или миграции.

## Жёсткие инженерные правила

- Не создавай второй источник истины для УГТ, заявок, документов или статусов.
- Следующее действие вычисляй из серверного состояния.
- Закрытые поля исключай backend-сериализацией; CSS не является защитой.
- Не используй ИИ для расчёта УГТ, статусов, списков документов или следующего действия.
- Не добавляй моки услуг, фиктивные цифры и неработающие CTA.
- Предварительный УГТ не участвует в фильтре подтверждённого уровня.
- URL — контракт состояния фильтров.
- Используй существующий ORM и миграции; никаких строковых SQL-запросов с пользовательскими значениями.
- Индексы добавляй под доказанные запросы и проверяй query plan.
- Не копируй код, графику, тексты, логотипы или CSS i.moscow.
- Не добавляй UI-библиотеку без необходимости; новый токен обязан работать в трёх темах.
- Смысл статуса не передавай только цветом.
- Максимум 25 итераций на тикет; при повторе одинакового сбоя остановись и зафиксируй блокер.

## Проверка каждого тикета

- Целевые frontend/backend тесты и отрицательные сценарии прав.
- Loading/empty/error/success состояния без моков.
- Отсутствие закрытых данных в публичных ответах.
- Deep links и восстановление после reload.
- Для UI: desktop/mobile и три темы.
- Для фильтров: URL, пагинация, сброс и некорректные параметры.

## P0 release gate

P0 готов только если:

- 01–07 имеют `Status: done`;
- frontend lint, typecheck, tests и production build зелёные;
- backend lint, tests и миграции зелёные;
- E2E проходит: оценка → объяснение → проект → следующий шаг → документы → автозаявка → менеджер → подтверждение → публичная карточка → реестр;
- два вида УГТ нигде не смешаны;
- приватные сведения отсутствуют в публичных API;
- три темы, mobile/desktop и accessibility smoke пройдены;
- типовые запросы реестра укладываются в нормативы базовой спеки;
- документация и статусы соответствуют реальности;
- все commits запушены.

## Итоговый отчёт Functional Validator

Кратко сообщи: что изменилось для пользователя и менеджера; как выглядит путь до следующего УГТ; статусы тикетов; прошедшие/проваленные проверки; адрес демо-сценария; ветку и SHA; подтверждение push; ограничения и P1. Не объявляй готовность только по наличию кода — готовность определяется поведением и зелёным release gate.
