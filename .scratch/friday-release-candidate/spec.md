# Friday Release Candidate — спецификация

Status: ready-for-agent

Целевая дата локального release candidate: **7 августа 2026 года**.  
Формальная дата сдачи MVP1: **31 августа 2026 года**.

## Problem Statement

Платформа «Технозрелость» уже содержит значительный объём frontend- и backend-кода, однако текущее состояние нельзя считать единым, чистым и доказуемо готовым продуктом. Реализованные механики, старые прототипы, несколько визуальных итераций, экспериментальные данные и инфраструктурные заготовки сосуществуют без одного актуального критерия готовности.

Пользователю нужен не очередной набор разрозненных функций, а стабильный локальный release candidate, который можно без переписывания бизнес-логики перенести на неизвестный заранее Linux-сервер. Кандидат должен демонстрировать полный путь технологического проекта от предварительной оценки до подтверждённого УГТ 9, обеспечивать управляемый документооборот, роли, реестры, приватность и менеджерскую верификацию. Архитектура не должна иметь известных ограничений, мешающих последующему тесту с 1 000 одновременно активных пользователей.

Одновременно требуется сохранить выбранный дизайн-код, устранить доказуемый мусор и визуальную несогласованность, поддержать три темы, закрыть основные риски доступа к документам и подготовить эксплуатационный контур: Docker, наблюдаемость, backup/restore, demo reset и нагрузочные сценарии.

## Solution

Создать единый deploy-ready локальный release candidate платформы на существующем стеке Next.js, FastAPI, PostgreSQL/pgvector, MinIO, Redis и Nginx. Все сервисы запускаются через параметризованный Docker Compose. Приложение и данные разделены; app-слой stateless и допускает несколько реплик; PostgreSQL поддерживает Primary/Replica; частые чтения и служебные состояния могут использовать Redis; файлы хранятся вне app-контейнеров.

Публичная зона показывает витрину продукта, центр, методологию, УГТ, дорожную карту и проверенные реестры. После регистрации любой пользователь может создать проект, пройти полный опросник из 22 рубежей и получить предварительную оценку УГТ 1–9. Официальный уровень автоматически подтверждается максимум до УГТ 2. Для уровней 3–9 платформа требует фиксированный универсальный комплект документов и окончательное решение менеджера центра.

Первичное подтверждение может сразу заявлять любой уровень при наличии доказательств всех предыдущих уровней. После первого подтверждения проект развивается только последовательно N→N+1. Загрузка последнего обязательного документа автоматически создаёт новую заявку. Каждая попытка неизменяема и содержит снимок конкретных версий документов. Менеджер подтверждает уровень либо возвращает структурированные причины и рекомендации.

Подтверждённые проекты публикуются при согласии владельца: УГТ 1–2 после автоматического подтверждения, УГТ 3–9 после решения менеджера. Публичная карточка может отдельно показывать предварительный уровень со статусом «Проходит верификацию». Реестры и фильтры используют только подтверждённый уровень.

106. Как владелец продукта, я хочу удалить только доказуемо мёртвый код, дубли, временные файлы и старые сборки, чтобы очистка не разрушила исторически полезные части.
107. Как владелец продукта, я хочу сохранить рабочий дизайн-код стартовой страницы, чтобы улучшение не превратилось в ребрендинг.
108. Как тестировщик, я хочу проверить Chrome, Firefox, Safari, Edge и Яндекс Браузер, чтобы поддержка была явной.

## Implementation Decisions

### Продукт и уровни УГТ

- Исходный чек-лист содержит 22 контрольных рубежа и является основой полной предварительной оценки УГТ 1–9.
- Расчёт детерминированный и версионируемый. ИИ не определяет уровень.
- Уровни достигаются непрерывно; критические рубежи обязательны. Действующие пороги должны быть сохранены либо изменены отдельным методологическим решением.
- Автоматически подтверждается официальный УГТ не выше 2.
- Предварительный УГТ 3–9 не является официальным и не используется для реестровых фильтров.
- Первичное подтверждение может присвоить заявленный уровень при проверке всех предшествующих доказательств. Последующие повышения идут только N→N+1.
- Для каждого перехода используется фиксированный универсальный список документов. Модель данных допускает будущие отраслевые наборы и версии методики.
- ИИ может объяснять требования, но не изменяет список документов и не принимает решение.

### Проекты, участники и роли

- Любой зарегистрированный пользователь может создать проект.
- Основная роль аккаунта определяет профессиональный профиль, рекомендации и профильный реестр, но не проектные полномочия.
- Системные роли менеджера и администратора назначаются только администрацией.
- Проектная роль выбирается отдельно и определяет проектные функции.
- `project_admin` — отдельное полномочие; первоначально его получает создатель, затем оно может быть передано.
- В проекте допускаются несколько участников одинаковой роли.
- Публичность меняет заказчик, одновременно имеющий `project_admin`.
- Договорное владение, правообладание и техническое администрирование — разные поля. Юридические поля меняет менеджер по основанию договора.
- Персональные приглашения одноразовые, криптографически случайные, ограничены сроком и набором допустимых ролей. Массовые приглашения имеют лимит и могут быть отозваны.
- Личные аккаунты отделены от организаций. Пользователь может состоять в нескольких организациях.
- Профессиональные профили и организации публикуются после заполнения, согласия и проверки менеджером.

### Документы и заявки

- Допустимые форматы: PDF, DOCX, XLSX, PNG, JPEG; лимит 25 МБ на объект.
- Фактический MIME проверяется; архивы и исполняемые файлы запрещены.
- Объекты получают внутренние имена; пользовательское имя хранится только как метаданные.
- Хранилище — MinIO с закрытыми бакетами и persistent volumes. PostgreSQL хранит метаданные, права, хеш и версии.
- Новый файл сначала карантинируется и проверяется ClamAV. Только чистый файл учитывается в комплекте.
- Версии неизменяемы. Заявка ссылается на конкретные версии.
- Полнота комплекта автоматически создаёт заявку независимо от автора последнего документа.
- После отказа новая попытка создаётся только для изменённого и снова полного комплекта.
- После подтверждения сохраняются верифицированные версии; остальные скрываются, восстанавливаются 30 дней и затем физически удаляются. Аудит хранит метаданные без содержимого.
- Решение менеджера включает структурированные критерии, документы, обязательную причину и рекомендации.
- Комментарии привязаны к заявке. Полноценный общий чат не создаётся.
- PDF-заключение демонстрационное, неизменяемое и явно не содержит УКЭП.

### Публикация и реестры

- Черновики приватны.
- УГТ 1–2 публикуются после автоматического подтверждения и согласия владельца.
- УГТ 3–9 публикуются после менеджерской верификации и согласия владельца.
- Предварительный уровень может быть показан отдельно по бесплатной настройке владельца.
- Публичная карточка показывает название, описание, отрасль, регион, подтверждённый УГТ, опциональный предварительный УГТ, статус верификации, дату обновления и не скрытых участников/организации.
- Документы, контакты, токены, внутренние причины отказов, комментарии и история заявок не публичны.
- Общий реестр и реестр технологий используют одну сущность проекта; технологии — подтверждённые проекты УГТ 7+.
- Обязательные фильтры: название, подтверждённый УГТ, статус верификации, отрасль, организация/участник, регион. Сортировки: дата обновления и УГТ.
- НИОКТР — отдельный read-only реестр записей, связанных с Удмуртией и её организациями; источник и дата импорта обязательны.
- Приватность проекта и участника реально работает, но в тестовом релизе бесплатна и сопровождается демонстрационным тарифным экраном.

### Уведомления и распределение работы

- Внутренние уведомления сохраняются в БД и доставляются в активный dashboard через SSE или эквивалентный односторонний realtime-канал.
- Браузер воспроизводит звук только после разрешённого пользовательского взаимодействия; пользователь может отключить звук, но не само уведомление.
- Проектное событие получает назначенный менеджер.
- Общеплатформенное неназначенное событие получают все подключённые менеджеры.
- «Взять в работу» — атомарная операция; задачу получает только один менеджер.
- Администратор видит общую очередь и может переназначить или вернуть задачу.
- Интеграционные события публикуются через outbox/очередь. Будущий адаптер Битрикс не влияет на основную транзакцию и умеет повторять отправку.

### Темы и интерфейс

- Стартовая страница является визуальным эталоном: технологичная тёмная основа, холодный синий акцент, крупная типографика, координатная сетка, данные и УГТ как центр.
- Существующий дизайн-код сохраняется; новая система с нуля не создаётся.
- Все компоненты используют семантические токены, без локально захардкоженных цветов.
- Темы: светлая технологическая, тёмная технологическая, удмуртская чёрно-красно-белая.
- Удмуртская тема использует восьмиконечный мотив как функциональную сетку, маркер, индикатор или паттерн. Герб не используется.
- Перед реализацией нового удмуртского направления создаются три реальные визуальные концепции одного экрана и фиксируется выбор пользователя.
- Публичная зона и основные пользовательские действия mobile-ready. Сложные менеджерские интерфейсы desktop-first, но адаптивны.
- Базовая цель доступности — WCAG AA для контраста, фокуса, клавиатуры и подписей.
- Интерфейс релиза русскоязычный; структура не должна блокировать будущую локализацию.
- Поддерживаемые браузеры: актуальные Chrome, Firefox, Safari, Edge, Яндекс Браузер; мобильные Chrome и Safari.

### Архитектура и масштабирование

- Стек сохраняется: Next.js App Router, FastAPI, PostgreSQL с pgvector, MinIO, Redis, Nginx, Docker Compose.
- Frontend и backend не используют локальное состояние, необходимое следующему запросу; app-реплики взаимозаменяемы.
- Nginx является внешней точкой входа и балансирует несколько app-реплик.
- PostgreSQL Primary обслуживает запись; Replica предназначена для безопасных read-запросов. Операции, требующие read-after-write, читают Primary.
- Redis используется только там, где измерена польза: кэш частых публичных чтений, rate limiting, распределённые служебные состояния и фоновые задания. Redis не является источником истины.
- Пулы соединений, лимиты воркеров и количество реплик задаются окружением.
- AI-запросы изолированы очередью, таймаутами и лимитами; сбой провайдера не нарушает основной продукт.
- Региональное распространение в текущем видении — отдельное комплектное развёртывание на регион, не multi-tenant SaaS. Региональные название, логотип, темы, контакты и методики конфигурируются без форка бизнес-логики.
- Цель серверного теста — 1 000 одновременно активных пользователей со смешанным профилем: 70% чтение витрины/реестров/карточек, 20% ЛК и опросник, 8% файловые операции, 2% менеджерские операции. AI тестируется отдельно.
- Цели обычного API: не менее 99% успешных запросов; p95 чтения до 500 мс; p95 записи до 1 секунды. Файлы и AI имеют отдельные нормативы.
- К пятнице готовится сценарий нагрузки; окончательное доказательство выполняется после получения серверной инфраструктуры и отдельного генератора нагрузки.

### Deployment и эксплуатация

- Docker Compose имеет профили `local` и `production`.
- На чистой Linux-машине оператор или AI-агент заполняет `.env` и запускает одну документированную команду.
- Deployment выполняет backup, проверку конфигурации, безопасные миграции, запуск контейнеров и health/readiness.
- Деструктивные миграции требуют отдельного подтверждения.
- Неуспешный health-check откатывает версию приложения; данные не изменяются импровизированными командами агента.
- Есть `.env.example` только с именами переменных. Секреты не передаются в спецификации, тикеты, логи или Git.
- Backup/restore покрывает PostgreSQL и MinIO; restore регулярно проверяется на тестовой схеме.
- Demo reset одной командой пересоздаёт тестовую схему, аккаунты, девять уровневых проектов, один последовательный проект, документы и очереди. В production-профиле reset заблокирован.
- Наблюдаемость: структурированные логи без персональных данных, health/readiness, метрики HTTP/БД/очередей/MinIO, Grafana и базовые алерты.
- Первый серверный стенд закрыт приглашением или дополнительной Nginx-защитой и использует только синтетические/обезличенные данные.
- TLS обязателен на сервере; MinIO-бакеты закрыты; диски и резервные копии должны шифроваться инфраструктурой. Ключи находятся вне репозитория.

### Очистка кода

- Удаляются только доказуемо мёртвый код, дубли, временные файлы, кэши и старые сборки.
- Старые модели, API, миграции, MVP0 и исторические материалы не удаляются без доказательства недостижимости и отсутствия миграционной ценности.
- Перед удалением проверяются импорты, роуты, runtime-вызовы, тесты и сборка.
- Пользовательские незакоммиченные изменения не перезаписываются и не смешиваются с очисткой.

### Порядок приоритетов при дефиците времени

1. Полный путь проекта и УГТ 1→9.
2. Документы, автозаявки и менеджерская верификация.
3. Права доступа, проектные роли и безопасность данных.
4. Публичные реестры и карточки.
5. Docker-развёртывание, backup/restore и тесты.
6. Три адаптированные темы.
7. Уведомления, комментарии и PDF-заключение.
8. Удмуртский орнамент, демонстрационные тарифы, Grafana и каркас Битрикс.

## Testing Decisions

- Главный тестовый шов — полностью развёрнутая система как чёрный ящик. Проверки взаимодействуют через браузер, HTTP API и файловые загрузки, а не с внутренними функциями.
- Главный E2E проходит: регистрация → профиль/организация → проект → полный опросник → официальный УГТ 2 → загрузка документов → автозаявка → менеджерское решение → последовательное повышение до УГТ 9 → реестры → экспорт.
- Отдельный E2E проверяет отказ, структурированные рекомендации, замену документа и новую неизменяемую попытку.
- Отдельный E2E проверяет приглашение, проектные роли, `project_admin`, скрытие проекта/участника и запреты доступа.
- Отдельный E2E проверяет неназначенную задачу и атомарное взятие двумя конкурентными менеджерами.
- Backend API-интеграционные тесты покрывают RBAC/IDOR, состояния заявок, версионирование, очистку, outbox, реестры, экспорт, карантин и аудит.
- Модульные тесты используются для чистых детерминированных правил: расчёт УГТ, полнота комплекта, переходы состояний, маршрутизация уведомлений.
- Существующие pytest-наборы и demo journey являются prior art и не заменяются; новые сценарии расширяют их.
- Frontend-проверки включают lint, TypeScript, production build, существующие node tests и browser E2E.
- Визуальный QA проходит ключевые публичные и служебные экраны в трёх темах, на desktop и mobile viewport; контраст и фокус проверяются автоматизированно там, где возможно.
- Browser matrix: Chrome как основной, smoke в Firefox, Safari, Edge и Яндекс Браузере; mobile smoke в Chrome/Safari.
- Миграции проверяются на чистой БД и на копии предыдущего состояния; schema `test` изолирована от `public`.
- File tests используют безопасные фикстуры допустимых форматов, неверный MIME, превышение размера и антивирусный тестовый маркер.
- Backup/restore тест физически восстанавливает БД и объекты и сравнивает контрольные суммы.
- Docker smoke проверяет запуск с нуля, readiness всех сервисов, повторный идемпотентный запуск и недоступность demo reset в production.
- Security gates: поиск секретов, проверка зависимостей, отрицательные RBAC/IDOR-тесты, отсутствие публичных MinIO URL и чувствительных данных в логах.
- Нагрузочный сценарий воспроизводит согласованный профиль 1 000 пользователей. Локально проверяется корректность сценария с меньшей нагрузкой; итоговые SLO подтверждаются на сервере отдельным генератором.
- AI тестируется со стабом/моком и отдельным живым smoke, чтобы внешний провайдер не делал основной suite нестабильным.
- Кандидат готов только при зелёных frontend lint/type/build/tests, backend ruff/pytest/migrations, E2E, Docker smoke, backup/restore и security gates.

## Out of Scope

- Реальные платежи, эквайринг, чеки и окончательные цены тарифов.
- Реальная интеграция с Битрикс; входит только событийный контракт/адаптерный seam.
- Email-верификация, SMTP, восстановление пароля и CAPTCHA.
- MFA; она обязательна до использования реальных данных, но не входит в пятничный релиз.
- CMS для публичных страниц.
- УКЭП, юридически значимая подпись и полный электронный документооборот.
- AI-проверка документов по утверждённым шаблонам центра.
- Динамическое формирование обязательных документов с помощью ИИ.
- Отраслевые варианты комплектов документов; используется один универсальный демонстрационный набор.
- Реальные персональные данные, закрытая информация предприятий и любые материалы ВПК.
- ФСТЭК-аттестованный контур, внешний пенетест и промышленное подтверждение 152-ФЗ.
- Multi-tenant SaaS и одна федеральная инсталляция для нескольких регионов.
- Подтверждение 1 000 пользователей на локальном компьютере; подтверждение выполняется на будущем серверном стенде.
- Свободная публичная регистрация на первом серверном стенде.
- Полноценный общий чат, видеосвязь и вложения в сообщениях.
- Полноценная распределённая трассировка.
- Международная/удмуртская локализация интерфейса.
- Массовый административный экспорт всей платформы.
- Автоматическое связывание внешних НИОКТР с профилями без проверки.
- Удаление устаревших моделей, API, миграций и исторических материалов без доказательства безопасности.

## Further Notes

- Файл «Чек-лист готовности проекта.docx» является источником 22 рубежей. Текущая реализация уже содержит версионированный шаблон и server-side расчёт; это нужно сохранить и проверить, а не переписывать без необходимости.
- Текущая документация сообщает о существующих механиках экспресс-оценки, менеджерских очередей, N→N+1, реестров, join-токена, RAG и 80 backend-тестах. Спецификация требует аудит фактического состояния перед созданием тикетов: «отмечено как сделанное» не равно «принято новым критерием».
- Репозиторий имеет незакоммиченные пользовательские изменения в `main`; вся работа выполняется только в изолированных worktrees.
- В пятничном релизе пользовательские данные тестовые. Это не отменяет архитектурных защит, но позволяет явно отложить юридические и инфраструктурные меры, которые невозможно честно подтвердить локально.
- Перед новым дизайном удмуртской темы действует отдельный визуальный gate: три направления и явный выбор пользователя.
- Любая реализация начинается только после отдельного согласования этой спецификации и следующего набора тикетов.
