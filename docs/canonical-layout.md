## 2. Канонические каталоги монорепо-цели

Целевая структура единого монорепо (по спеке `.scratch/repo-hygiene/spec.md`):

| Каталог | Назначение |
|---|---|
| `frontend/` | Next.js-приложение (канонический источник — worktree `technozrelost-frontend`) |
| `backend/` | FastAPI-приложение (канонический источник — worktree `technozrelost-backend`) |
| `infra/` | Docker compose, deploy/backup/restore, nginx, postgres, prometheus, grafana |
| `docs/` | Документация, агентские руководства, canonical-layout (этот файл), будущий `docs/archive` |
| `tests/` | Сквозные/интеграционные тесты уровня монорепо |
| `.github/workflows/` | CI (на момент тикета 02 в дереве отсутствует) |

**Важно:** каталоги `frontend/`, `backend/`, `infra/`, `tests/` физически в корне репозитория **ещё не существуют**. Приложения живут в изолированных worktree на отдельных ветках (`technozrelost-frontend`, `technozrelost-backend`). В рамках тикета 02 они объявляются каноническими источниками, а физическая консолидация выносится в отдельный тикет (см. раздел 3).

**Консолидация НЕ выполнена — раздельные ветки/worktree не являются завершённой консолидацией.** Это текущий (промежуточный) способ существования репозитория: приложения доступны в двух отдельных checkout'ах на разных ветках, а не в едином рабочем дереве. Целевое состояние — единый рабочий checkout с каталогами `frontend/`, `backend/`, `infra/`, `tests/` в корне; оно НЕ достигнуто и будет достигаться только будущим миграционным тикетом (раздел 3). До тех пор ни одна ветка/worktree не «представляет» монорепо сама по себе.

## 3. Обоснование: почему физическая консолидация — отдельный будущий тикет (expand → migrate → contract)

В этом запуске **безопасно невозможно** свести приложения в единое монорепо-дерево:

- Оба канонических worktree имеют **грязные рабочие деревья** (код на диске ≠ HEAD): backend — 591 D / 20 ?? / 1 M, frontend — 52 M / 15 ?? / 2 D (зафиксировано в тикете 01, `.scratch/repo-hygiene/inventory-report.md`). Любой merge/checkout на этом состоянии рискует потерять локальные untracked-изменения.
- Деревья живут на **разных ветках** (`codex/recovery-frontend`, `release/friday-rc`) с разными историями; корень — на `codex/видениепроектадо310826` (c2964a2) с 138 незакоммиченными изменениями, включая 127 удалений в legacy-папке.
- Развёртывание/перемещение кода = изменение продуктовых путей и точек сборки — это противоречит ограничению тикета 02 («НИЧЕГО не удаляй», правки только в $WT).

Поэтому применяется стратегия **expand–migrate–contract** без промежуточного сломанного состояния:

1. **Expand (этот тикет, 02):** фиксация канонических путей документацией (`README.md`, `docs/canonical-layout.md`), усиление `.gitignore`. Никакого движения кода — сборка существующих приложений не ломается.
2. **Migrate (будущий тикет):** консолидация worktree-деревьев в `frontend/` и `backend/` корня после очистки рабочих деревьев (тикет 03) и согласования владельцев; перенос ценных исторических материалов в `docs/archive`.
3. **Contract (будущий тикет):** удаление legacy/конкурирующих деревьев и веток, единый CI на канонических путях, удаление рудиментов.
