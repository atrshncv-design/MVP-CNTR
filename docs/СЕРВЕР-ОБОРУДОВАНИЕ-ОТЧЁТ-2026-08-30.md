# Требования к серверному оборудованию — платформа «Технозрелость»

**Дата отчёта:** 30.08.2026  
**Проект:** цифровая платформа «Технозрелость» (ЦНТР УР, ГОСТ Р 58048-2017)  
**Формат:** покупка собственного железа; допустим x86 Intel/AMD; локальный LLM-контур сейчас не требуется (всё AI — внешние API)  
**Бюджетная рамка:** ≤ 1 000 000 ₽ за железо; если уложиться в ~600 000 ₽ — приоритет  
**Сценарии:** рассчитаны A/B/C/D

---

## 1. Краткий вердикт

Для пилота и production-первого года достаточно **одного производительного сервера на AM5/EPYC 4004 (16C/32T, 128 ГБ ECC DDR5, 2×3,84 ТБ enterprise NVMe RAID1)** стоимостью ~420–520 тыс. ₽.

Для выполнения цели **RTO ≤ 1 час** и аптайма 99,9% рекомендуется **два одинаковых узла** (~600–700 тыс. ₽): один работает, второй — горячий standby / read replica, на который за час можно поднять весь контур. Один сервер — это единая точка отказа, RAID и ИБП её не устраняют.

**GPU не нужен** — в коде нет локальных нейросетей. Эмбеддинги считаются sha256-хешом (`app/core/embeddings.py`), LLM выключен по умолчанию и идёт через внешний API (`app/services/ai_assistant.py`). Отдельный LLM-сервер рассчитан ниже как **опция** (~300–550 тыс. ₽), но он не пересекается с основным.

**Mac mini** — удобен лично вам как стенд и cold-standby, но не годится в качестве единственного production-сервера: нет ECC, IPMI, горячей замены дисков, резервирования БП, Docker на macOS работает через виртуалку.

10 000 одновременных пользователей в ближайшие полгода не ожидается; поэтому закупка под пилот/production с возможностью докупить узел БД в 2027–2028 — экономически разумный путь.

### 4.2. Что можно безопасно держать на одном сервере на этапе MVP

На одном хосте (сценарии A/B) можно объединить **всё**, включая Primary и Replica, если цель — пилот и RTO не критичен. Но начиная со сценария C, желательно разносить Primary и Replica на разные узлы.

### 4.3. Что желательно разделить при росте

- PostgreSQL Primary ↔ Replica (разные физические узлы при C и выше).
- LLM-контур (если появится) — **отдельный сервер с GPU** по требованию пользователя.
- Offsite-бэкапы — вне площадки (S3 в РФ).

## 5. Расчёт CPU, RAM, GPU, дисков и сети

### 5.1. Методика

**RPS:**

- Нормальный профиль: `RPS = VU / 7 с` (из интервью CTO).
- Стресс-профиль: `RPS = VU × 0,57` (методика `infra/README-LOADTEST.md` для 1000 VU).

**CPU:**

- Суммируем vCPU-бюджет всех сервисов, затем делим на целевую загрузку **60 %**.
- Это даёт запас под пики, сборку образов и антивирусное сканирование.

**RAM:**

- Сумма сервисов × **1,3** (запас ОС/буферы/пики) → округляем вверх до доступных модулей.

**Диск:**

- Сумма томов × **1,3** (запас свободного места) → при RAID1 делим пополам.
- PostgreSQL и WAL должны быть на NVMe с PLP.

**Сеть:**

- Пиковая полоса ≈ `RPS × средний размер ответа`.
- До сценария C достаточно 1 GbE; для D — 2,5–10 GbE.

### 5.2. Компонентный бюджет для сценария C (2 000 одновременных)

48 потоков → физический **16C/32T** с высокой частотой (EPYC 4584PX 3,7–5,7 ГГц) покрывает с запасом.

### 5.3. GPU

**Основной сервер: GPU не требуется.**

Формула VRAM для опционального локального LLM-контура:

```
VRAM ≈ (params × bytes_per_param × 1,2) + KV_cache
bytes_per_param: FP16=2, BF16=2, INT8=1, INT4=0,5
```

- 7B INT4: ~7×0,5×1,2 ≈ **4,2 ГБ** → подойдёт GPU 8 ГБ.
- 14B INT4: ~14×0,5×1,2 ≈ **8,4 ГБ** → подойдёт 12–16 ГБ.
- 32B INT4: ~32×0,5×1,2 ≈ **19 ГБ** → нужно 24 ГБ.

### 8.4. Почему ECC и почему UDIMM/RDIMM

- **ECC** — обязательна для PostgreSQL: битовая ошибка в памяти БД → тихое повреждение страницы, WAL и репликация распространят порчу. Non-ECC допустима только на стенде.
- **UDIMM** — для AM5/EPYC 4004 (2-канальный контроллер, нерегистровые модули).
- **RDIMM** — для SP5/SP6 (EPYC 9004/8004), позволяет 12/8 DIMM и терабайты памяти.

## 9. Схема размещения сервисов

### 9.1. Практичная схема для MVP/пилота (B)

```
[Интернет] → [nginx :443] → [frontend :3000] ─┐
                                               │
                                            [backend ×2 :8000]
                                               │
                     [PostgreSQL Primary] ←──[pgvector]──→ [Replica]
                                               │
                                          [MinIO] [ClamAV] [Redis] [Prom/Grafana]
                                          [backup-timer] [wal-offsite] [alerter]
```

Всё на одном физическом узле. RTO зависит от восстановления с бэкапа.

### 9.2. Production-схема (C/D) — два/три узла

```
                         [Узел 2 — standby / replica]
                         Primary replica + standby app + backup target
                         PostgreSQL Replica (hot standby)
                         WAL-archive, backups
                                  │
                         10G direct link
                                  │
[Интернет] → [nginx] → [frontend] → [backend ×N] → [PostgreSQL Primary]
              │           │           │              [MinIO]
              │           │           │              [ClamAV]
              │           │           │              [Redis]
              │           │           │              [Prom/Grafana]
              │           │           │              [backup/alerter]
              │        [Узел 1 — active]
              │
        [Offsite S3 через rclone crypt]
```

### 9.3. Единые точки отказа

| Компонент | Риск | Митигация |
|---|---|---|
| Один сервер | Полный простой | Второй узел (C2) |
| Один БП | Простой до замены | ИБП + второй узел |
| Один NVMe | Потеря данных | RAID1 |
| Один switch/uplink | Нет связи | 2 uplink/канала |
| PostgreSQL Primary | Нет записи | Replica + failover |
| MinIO single node | Нет файлов | Репликация/бэкапы |

## 10. Резервное копирование и отказоустойчивость

### 10.1. Цели

| Параметр | Значение | Статус |
|---|---|---|
| RPO | ≤ 5 минут | Цель конфигурации, не подтверждённый SLA |
| RTO | ≤ 1 час | Цель конфигурации, не подтверждённый SLA |
| Аптайм | 99,9 % | ≈ 8 ч 45 мин простоя/год |

### 10.2. Стратегия 3-2-1

- **3** копии данных: Primary, локальные бэкапы, offsite.
- **2** разных носителя: NVMe + offsite S3/HDD.
- **1** копия вне площадки.

**RAID1 — не бэкап**, это только защита от отказа диска.

### 10.3. Резервное копирование

| Тип | Частота | Хранение | Инструмент |
|---|---|---|---|
| Логический дамп | Ежедневно в 03:15 UTC | 14 копий локально | `pg_dump -Fc` |
| Физический бэкап | Ежедневно | 14 копий локально | `pg_basebackup -X stream` |
| WAL-архив | Непрерывно, архив каждые 60 с | Локально + offsite | `archive_command` + `wal-offside-sync.sh` |
| MinIO mirror | Ежедневно | Локально + offsite | `mc mirror` / python-minio |
| Offsite | После каждого бэкапа | S3/Yandex/Selectel/VK через `rclone crypt` | `rclone copy` |

### 10.4. Восстановление

- **Отказ диска:** RAID1 выдерживает; замена диска, rebuild.
- **Отказ сервера:** переключение на узел 2, подъём сервисов за ≤ 1 ч (C2). При C1 — восстановление с бэкапа: RTO может быть 2–6 ч.
- **Отказ площадки:** восстановление из offsite на новом железе/ЦОД. Потеря данных ≤ 5 мин при работающем WAL-offsite.
- **PITR:** уже есть репетиция `reports/pitr-rehearsal-2026-08-29.txt` — PASS.

## 13. План масштабирования и модернизации

### 13.1. Первый этап: сейчас — пилот (B)

- Докупить **узел БД класса EPYC 8224P/8424P + 256 ГБ RAM**.
- Вынести MinIO в отдельный узел или S3-совместимое хранилище.
- Партиционирование `nioktr_cards` по секторам/регионам.

### 13.4. Что закладывать сразу правильно

| Компонент | Почему |
|---|---|
| Платформа AM5 / SP6 | Сокет и чипсет не меняются при апгрейде CPU |
| 4+ DIMM-слота / 8+ DIMM-слотов | Чтобы докупить RAM, а не менять платы |

| 2×U.2 / M.2 отсека | RAID1 NVMe для БД и WAL |
| БП с запасом 30–40 % | Пики ClamAV/деплоя |
| ИБП с чистым синусом | Защита PostgreSQL от внезапного отключения |

### 13.5. Горизонтальное масштабирование

- backend/frontend: увеличение реплик в `docker-compose.prod.yml`.
- PostgreSQL: read replicas + pgbouncer; при D — шардирование/партиционирование.
- MinIO: переход на кластер MinIO или внешнее S3.
- SSE: Redis pub/sub (нужно сначала добавить пакет `redis`).
