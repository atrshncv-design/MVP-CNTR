## 1. Краткий вердикт

Практичная основная рекомендация в пределах ожидаемого бюджета — **два одинаковых физических
сервера** по 16 физических ядер, 128 ГБ ECC DDR5, с BMC/IPMI, зеркалом из двух enterprise
TLC SSD с защитой от потери питания и двумя 10GbE-интерфейсами на каждом. Расчётный комплект
на AMD EPYC 4564P и ASRock Rack B650D4U3-2L2Q стоит **966 000 ₽ (оценка)**. Все российские
цены в отчёте являются оценками на 2026-08-30: публичные предложения с подтверждённым
наличием не найдены (`.autopilot/2026-08-30-server-infrastructure-requirements--wip/work/hardware-procurement.md:123-127`).
До покупки нужны минимум два КП с точными P/N, НДС, наличием и гарантией.

Два узла вместе являются обоснованным кандидатом на целевые 300–500 HTTP RPS и 10 000
одновременно вошедших пользователей. Это не гарантия до production-like benchmark. При
отказе одного узла бюджетная схема честно переходит в **деградированный режим около
250–300 RPS**, а не сохраняет гарантированные 500 RPS. Полные 500 RPS при N-1 требуют по
24–32 физических ядра на каждом узле и выходят в отдельный, пока не оценённый по цене класс.

GPU сейчас покупать не следует: LLM вызывается через внешний OpenAI-compatible API, а
эмбеддинги вычисляются CPU-hashing алгоритмом (`technozrelost-backend/app/services/ai_assistant.py:32-44`,
`technozrelost-backend/app/core/embeddings.py:16-30`). Один сервер допустим для MVP с
принятым простоем; три сервера — следующий шаг для quorum и обслуживания, но не стартовая
необходимость.

Цели 99,9%, RPO 5 минут и RTO 1 час требуют внешней резервной копии, физического разделения
узлов, проверяемого переключения и restore drill. Два узла без внешнего witness не дают
автоматический безопасный DB failover: promotion должен быть ручным либо использовать
третий независимый голос. RAID, UPS, dual PSU и виртуализация не заменяют второй узел и
offsite backup.

**Статус измерений:** старый прогон показал около 55–61 RPS при ≈0,89 CPU core backend и

## 4. Архитектура и профиль нагрузки

```text
Internet -> nginx/TLS -> Next.js SSR
                     -> FastAPI x2 -> PostgreSQL Primary (write/read-after-write)
                                     -> PostgreSQL Replica (safe reads)
                                     -> Redis (SSE/pub-sub)
                                     -> MinIO -> ClamAV
                                     -> pgvector + CPU hashing RAG
                                     -> external OpenAI-compatible LLM
Monitoring: Prometheus/Grafana; operations: scheduler, backup, WAL-offsite, alerter
```

| Компонент | Постоянно | Пик | CPU/RAM/I/O/network | Отдельный узел сейчас |
|---|---|---|---|---|
| nginx/Next.js/FastAPI | да | HTTP/SSR/auth | CPU и connections; stateless scale-out | нет, по экземпляру на узел |
| PostgreSQL Primary/Replica | да | write/read burst, checkpoint | RAM и low-latency I/O критичны | физически разделить по узлам |
| Redis/SSE | да | fan-out/10K connections | RAM/network, высокая single-core частота | нет; HA после теста |
| MinIO/ClamAV | да | загрузки до 25 MiB | disk/network и CPU сканирования | совместно допустимо, по узлам |
| pgvector/RAG hashing | по запросу | ingest/query | DB I/O/CPU/RAM; VRAM 0 | нет до измеренного bottleneck |
| scheduler/backup/WAL | периодически | backup/reindex | disk/network | backup destination вне узлов |
| monitoring/logs | да | incident/query | RAM/storage | совместно, retention ограничить |
| CI/staging | по релизу | build/test | CPU/RAM/I/O | вне production |
| Local AI/OCR/reranker | отсутствует (`.autopilot/2026-08-30-server-infrastructure-requirements--wip/work/evidence-capacity.md:76-80`) | условно | потребовал бы GPU/CPU | не выделять заранее |

Текущие лимиты API в Compose — по 1 CPU/2 GiB на реплику
(`technozrelost-backend/infra/docker-compose.prod.yml:184-203`) — факт конфигурации, но не
доказательство достаточности. Full-text обслуживает PostgreSQL; очередь отсутствует
(`.autopilot/2026-08-30-server-infrastructure-requirements--wip/work/evidence-capacity.md:76-80`), а
scheduler внутри процесса требует singleton/lock проверки перед увеличением workers.

## 5. Расчёт CPU, RAM, GPU, дисков и сети

**CPU.** Из устаревшего baseline: `60 / 0,89 = 67,42 RPS/core`. Плановая формула:
`CPU_api = RPS × (0,89 / 60) × K`, где `K=1,5–2,5` покрывает TLS, auth, logging,
неидеальное масштабирование, фон и отказ узла.

| RPS | K | Арифметика | API physical cores |
|---:|---:|---:|---:|
| 300 | 1,5 | `300×0,014833×1,5` | 6,68 |
| 300 | 2,5 | `300×0,014833×2,5` | 11,13 |
| 500 | 1,5 | `500×0,014833×1,5` | 11,13 |
| 500 | 2,5 | `500×0,014833×2,5` | 18,54 |

К API добавляются DB, ClamAV, storage, Redis, monitoring и ОС. SMT threads не считаются
физическими ядрами. Для shared load достаточно проверять 16 cores/node; для 500 RPS на
одном узле нужен кандидат 24–32 cores/node. Высокая частота ≥3,5 GHz важна API, SSR, Redis
и DB latency; backup/monitoring важнее aggregate cores и I/O.

**RAM.** `RAM_required = sum(working_sets)/utilization_limit`. На узел: PG 32 + API 8 +
MinIO 4 + ClamAV 4 + Redis 4 + frontend/nginx 3 + monitoring 4 + OS 4 = 63 GiB.
`63/0,75=84 GiB`, `63/0,70=90 GiB`: минимум 96, рекомендация 128 ГБ. Failover:
API 16 + PG 48 + остальное 23 = 87 GiB; `87/0,70=124,3 GiB`, поэтому 128 ГБ — нижняя
граница degraded режима. ECC обязательна для production DB; non-ECC допустима только для
непродуктивного стенда. RAM и VRAM не смешиваются; для текущего AI VRAM = 0.

**Диски.** `1 GiB/day × 365 × years × 1,30 / 0,80`: 593 GiB на год и 1 779 GiB
(1,74 TiB) на три года с версиями/метаданными и 20% free. С допущениями DB/index/WAL 1 TiB
и logs/temp/monitoring 0,5 TiB получается 3,24 TiB operational usable; класс 4 TiB usable
требует 8 TiB raw в RAID1. Стартовый бюджетный BOM даёт лишь 1,92 ТБ usable/node и должен
расширяться до RAID10 после измерения роста. Primary storage: enterprise TLC, PLP, ≥1 DWPD;
QLC/consumer без PLP не подходит. RAID не backup.

**Сеть.** `Mbps = RPS × payload_KiB × 8 / 1024`.

| RPS | 50 KiB | 100 KiB | 250 KiB |
|---:|---:|---:|---:|
| 300 | 117,19 Mbps | 234,38 Mbps | 585,94 Mbps |
| 500 | 195,31 Mbps | 390,63 Mbps | 976,56 Mbps |

Верхняя точка с 30%: `976,56×1,3=1 269,53 Mbps`; условная цель WAN ≥2 Gbps, если
250 KiB подтвердится. Между узлами — 10GbE с отдельными VLAN для replication/backup и BMC;
25GbE только после saturation/backup-window теста.

**LLM.** `1000/3600=0,2778 RPS`. По Little's Law при latency 5/10/30/60 с concurrency
равна 1,39/2,78/8,33/16,67; semaphore 20–25 — целевое допущение. GPU не нужен.

## 6. Сценарии нагрузки: MVP, пилот, production, рост

Все cardinality, кроме явно заданных C concurrency/RPS/LLM и A–C file growth, являются
**допущениями**.

| Поле | A: MVP | B: пилот | C: production | D: рост 2–3 года |
|---|---|---|---|---|
| Registered/DAU/MAU | 2k/300/1k | 20k/3k/10k | 100k/20k/60k | 300k/60k/180k |
| Concurrent | 200 | 2 000 | **10 000 цель** | 20 000 |

## 9. Схема размещения сервисов

Ровно шесть категорий из брифа; два и три узла являются подвариантами категории 2, а
AI-host — подвариантом категории 6.

| Категория | Подвариант | Perf | CAPEX/OPEX | Надёжность/scale | Обслуживание/security | Recovery/SPOF |
|---|---|---|---|---|---|---|
| 1. Один физический сервер | один host | средняя | низкий/низкий | низкая/вертикально | просто; hardening обязателен | долго; host/site SPOF |
| 2. Несколько серверов с разделением ролей | два сервера | высокая | средний/низкий | хорошая; degraded N-1 | умеренно; ручной promotion/witness | 5–15 min target; site/switch SPOF |
| 2. Несколько серверов с разделением ролей | три сервера | высокая | выше/средний | quorum/N+1, лучше scale | сложнее | быстрее; site SPOF остаётся |
| 3. Арендованный dedicated server | dedicated | высокая | средний/средний | зависит от provider | provider controls | provider/site SPOF |
| 4. Облачная инфраструктура | cloud | высокая | низкий старт/высокий OPEX | хорошая | IAM/152-ФЗ/egress сложнее | быстро; provider/account SPOF |
| 5. Гибридная схема | hybrid | высокая | высокий/высокий | гибкая | максимальная сложность/WAN | WAN/integration SPOF |
| 6. Размещение AI/GPU отдельно | AI-host | AI высокая | высокий/высокий | AI масштабируется отдельно | нужен GPU ops | AI host SPOF; core работает без AI |

Практичная MVP-схема:

```text
Internet -> [SERVER A: nginx + Next.js + FastAPI + PG + Redis + MinIO + ClamAV]
                                  |
                                  +--> encrypted offsite backup
                                  +--> external cloud LLM
SPOF: server A, switch/channel/site. Короткий простой принят.
```

Рекомендуемая production-схема:

```text
                    +--> SERVER 1: nginx/app + PG Primary + MinIO/ClamAV
Internet -> switch -|
                    +--> SERVER 2: nginx/app + PG Replica + MinIO/ClamAV
                         | 10GbE WAL/object replication
External witness --------+          +--> encrypted offsite backup/site
External cloud LLM <---------------- app (no local GPU)
```

Stateless traffic делится между узлами. Файлы реплицируются явно; DB promotion при двух
узлах ручной либо через внешний witness для защиты от split-brain. Один switch и одна
площадка остаются SPOF. Третий узел добавляется после benchmark для quorum/maintenance, а
не как преждевременный кластер.

## 10. Резервное копирование и отказоустойчивость

Критичны PostgreSQL, MinIO-объекты, секреты и конфигурация. Compose имеет volumes Primary/WAL,
daily backup sidecar и rclone/offsite markers (`technozrelost-backend/infra/docker-compose.prod.yml:42-50`,
`technozrelost-backend/infra/docker-compose.prod.yml:239-246`,
`technozrelost-backend/infra/docker-compose.prod.yml:289-299`), но наличие механизма не
доказывает успешный restore.

- Цель: nightly base/full, continuous WAL с `archive_timeout≤60s`, offsite sync ≤5 min.
- Retention target: 14 daily, 8 weekly, 12 monthly logical/object copies; уточнить по политике.
- 3-2-1: production data, локальная копия на другом media и encrypted immutable offsite вне
  обоих узлов. RAID, replica и snapshot по отдельности backup не заменяют.
- Ежемесячный выборочный restore; ежеквартальный полный restore/failover drill.
- Отказ диска: RAID rebuild и замена hot-swap без потери backup. Отказ сервера: controlled
  PG promotion, stateless reroute, object verification. Отказ площадки: восстановление из
  offsite на резервном оборудовании; только drill доказывает RTO.

Backup capacity: operational 3,24 TiB. Два weekly full + 28 daily changes по допущению 1%
+ WAL 0,5 TiB: `2×3,24 + 28×0,0324 + 0,5 = 7,887 TiB`; с 20% free:
`7,887/0,8=9,86 TiB`: **9,86 TiB уже включает 20% свободного резерва**. Для закупки
округлить вверх до класса 12 TiB usable как headroom сверх расчётного минимума, а не
добавлять к 9,86 TiB ещё 20%. Change rate, compression и WAL неизвестны.

99,9% за 30 дней допускает `30×24×60×0,001=43,2 min` (43,8 min в среднем месяце).
RTO 1 час превышает этот месячный бюджет и является DR ceiling, не гарантией SLA. Routine
failover должен целиться в 5–15 минут; RPO 5 минут подтверждается WAL markers и restore.

## 13. План масштабирования и модернизации

1. До закупки измерить реальный профиль и получить КП/QVL/build sheet.
2. Сразу правильно выбрать socket/platform, BMC, ECC, airflow, PSU reserve, PCIe lanes,
   DIMM slots, hot-swap bays и dual 10GbE: их поздняя замена дорога.
3. После запуска мониторить CPU/RAM, DB locks/cache/temp, SSD wear/free, WAL, replica lag,
   object replication, SSE и канал.
4. При росте данных добавить два одинаковых SSD на узел и перейти к RAID10 после проверенного
   backup/restore; расширить offsite capacity. RAM на AM5 может потребовать замены всех DIMM.
5. При CPU saturation добавить FastAPI replicas и DB pooling/PgBouncer; не масштабировать
   scheduler workers без singleton/leader механизма.
6. Для отказоустойчивого обслуживания добавить внешний witness или третий физический узел.
7. При DB bottleneck отделить DB/storage от stateless app; горизонтальное масштабирование
   выбирается по measured bottleneck, а не заменяется бесконечным vertical upgrade.
8. Локальный GPU/AI рассматривать последним, только после model/context/tokens/s/TCO test.
   Break-even: `GPU+host CAPEX / (cloud token cost/month - electricity - support)`; при
   знаменателе ≤0 локальный inference не окупается.

## 14. Какие benchmark-тесты нужно провести перед закупкой

В рамках отчёта сервисы не запускались и опасный/длительный load test не выполнялся. Причина
зафиксированного stub — отсутствие host 4 vCPU/12 GB (`reports/loadtest_report.json:3-5`).
Неизвестны full idle, per-service CPU/RSS, IOPS/throughput, SSE memory, lag, replication и
backup window. Существующий harness задаёт 1 000 VU, 120 s, success ≥99%, p95 read ≤500 ms,
write ≤1 s (`technozrelost-backend/scripts/loadtest.py:13-22`,
`technozrelost-backend/scripts/loadtest.py:41-42`).

План на кандидатном оборудовании:

1. Smoke и idle 30 минут: CPU/RSS/page cache/container limits, temperatures, wall power.
2. Ступени 300 и 500 RPS с mix 70/20/8/2, auth/read/write и payload 50/100/250 KiB.
3. 10 000 SSE/TLS connections: fd, nginx/API RSS, Redis memory/network, reconnect storm.
4. Upload 1/5/25 MiB и concurrency: ClamAV p95, MinIO throughput, temp space, fail-closed.
5. PostgreSQL: pool wait, CPU, locks, cache hit, temp spill, WAL rate, replica lag; `fio`
   безопасным профилем для fsync p95/p99, random IOPS, sequential throughput и RAID rebuild.
6. LLM latency 5–60 s, timeout/error injection, semaphore 20–25, fallback без GPU.
7. One-node failure: stateless reroute, controlled promotion, degraded throughput 250–300
   RPS; отдельно проверить дорогой N-1 target 500 RPS.
8. Backup window, encrypted offsite, single-object/DB restore и полный site-loss drill.

Собирать p50/p95/p99, errors, success, CPU cores, RSS, disk latency, network/WAL и power.
Принять только при success ≥99%, latency targets, CPU steady ≤60%, RAM ≤75%, disk ≤80%,
RPO ≤5 min и проверенном routine failover 5–15 min. Пересчёт:
`core_cost=measured_cores/measured_RPS`; `CPU=target_RPS×core_cost×K`;
`RAM=peak_working_sets/0,70`; `storage=(daily_change×retention+full+WAL)/0,8`;
`network=measured_bytes/RPS×target_RPS×8×1,3`.
