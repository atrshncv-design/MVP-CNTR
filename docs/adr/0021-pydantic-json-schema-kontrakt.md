# ADR 0021 — Pydantic + JSON Schema как контракт шаблона

**Дата:** 2026-09-03
**Статус:** принят
**Tier:** T2 — reestr-kompetencii-udgu

## Контекст
Нужен единый машиночитаемый контракт между тремя артефактами: Excel-шаблоном (R19), пайплайном ingest (R22) и будущим маппингом в реестры платформы (R20: кафедра→Organization, задел→competency, оборудование→Equipment, РИД→Patent, услуга→ServiceOffering). Стек бэкенда уже Python/FastAPI + Pydantic; валидация должна давать построчные сообщения «строка 12 листа 04: поле год — ожидается 1900–2026» (R19.1).

## Решение
Источник истины — Pydantic-модели `UdguImport { university, departments[], priorities[], mission, equipment[], patents[], services[], people[], raw_refs[] }` с типизацией (`trl: int 1–9 опционально`, `competencies: list[str]` как в платформе, даты/годы, обязательность по листам). Из них генерируется `schema/udgu_template.schema.json` — публикуемый контракт для внешних потребителей. Excel-валидация (списки/форматы) — лишь UX-дружелюбный дубль, не источник истины.

## Почему (с отвергнутыми)
- **Только JSON Schema без Pydantic — отвергнута:** дублирует валидацию (схема ≠ код пайплайна), нет автодополнения и mypy-строгости, уже есть Pydantic в бэкенде — единообразие дешевле.
- **Только openpyxl-валидация в Excel — отвергнута:** не покрывает сырые данные, не даёт `report.json` с типами, ломается при ручном редактировании ячеек.
- **Dataclasses + ручные проверки — отвергнуты:** нет генерации схемы, нет сообщений уровня поля, больше кода без выгоды.
- **Отдельный DSL/Excel-macro — отвергнут:** привязка к Microsoft-стеку, непереносимо в CLI, не тестируется в `pytest`.

## Последствия
- Плюс: одна модель — и для чтения листов, и для генерации схемы, и для будущего маппинга; консистентные ошибки уровня поле/строка/лист; соответствие платформе без БД-зависимости.
- Минус: версионирование схемы при расширении листов (`08_...`) — нужна политика semver и fallback «нераспознанный лист — проигнорирован»; зависимость `pydantic`/`pandas`/`openpyxl` в `scripts/udgu_ingest`.
- Цена: «грязные» поля остаются строками с последующей нормализацией; строгая типизация не означает строгий вход — пайплайн толерантен и отчитывается, а не падает.
