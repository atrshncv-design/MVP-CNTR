# ADR 0046: Token/session blocklist и отзыв сессий

Статус: proposed — решение владельца требуется

Тема: что происходит с уже выданным access-токеном после logout, смены роли, отзыва
доступа или подозрения на компрометацию. Решение не принято, механизм не реализовывался.

## 1. Текущее состояние

Подтверждено:

- После logout отзывается только refresh; access продолжает действовать до истечения срока
  (~55–60 минут по окну клиента) — finding SEC-05 в
  `docs/audit/2026-09-21-production/09-final/findings.json`, разбор в
  `docs/audit/2026-09-21-production/05-security/security.md` и
  `docs/audit/2026-09-21-production/09-final/README.md` (окно logout отмечено там же).
- Refresh-ротация атомарная, семейство отзывается при повторном использовании
  (ADR-0029, `technozrelost-backend/app/api/v1/auth.py`); хранение —
  `expires_at` / `revoked_at` (`docs/audit/2026-09-21-production/04-database/db-model.md`).
- Срок жизни access задаётся конфигурацией (`ACCESS_TOKEN_TTL_MINUTES`,
  `REFRESH_TOKEN_TTL_DAYS` — имена ключей из `technozrelost-backend/.env.example` и
  `technozrelost-backend/app/core/config.py`).
- Серверного blocklist/deny-list для access нет; аудит прямо называет это осознанным
  JWT-компромиссом с коротким TTL.
- Другой, независимый механизм уже существует и работает: одноразовый билет для SSE с TTL
  и запретом токена в query (ADR-0028, `technozrelost-backend/app/api/v1/realtime.py`).
  Это precedent для серверного состояния с коротким TTL.
- Клиент хранит действия офлайн-очереди без `Authorization` и подставляет токен в момент
  отправки (`technozrelost-frontend/src/features/offline/queue.ts`), то есть отзыв на
  сервере влияет на отправку отложенных действий.
- Redis в production обязателен (fail-fast в конфигурации), в dev/test допускается
  `not_configured`; для троттлинга входа уже есть fallback на память
  (`technozrelost-backend/app/api/v1/auth.py`).

UNKNOWN (не утверждается):

- Реальная частота злоупотребления украденным access-токеном — измерений нет.
- Готовность принять дополнительную зависимость каждого авторизованного запроса от
  хранилища отзыва.

## 2. Варианты

- **A. Принять риск с коротким TTL** (рекомендация аудита SEC-05). Последствия: ноль
  дополнительной работы и ноль новых зависимостей; окно злоупотребления украденным
  access остаётся, а «отзыв доступа сотруднику» возможен только по истечении TTL либо
  через отзыв refresh-семейства.
- **B. Короткоживущий blocklist идентификаторов выданных токенов** с проверкой на каждом
  авторизованном запросе, в Redis с ограниченным TTL и памятьным fallback. Последствия:
  мгновенный отзыв logout и смены роли, но каждый запрос получает дополнительную проверку,
  появляется требование к поведению при недоступности хранилища (fail-open или fail-closed)
  и риск неограниченного роста множества.
- **C. Серверные сессии** вместо stateless access. Последствия: полный контроль отзыва и
  возможности «выйти со всех устройств», но появляется состояние на каждом запросе,
  миграция схемы и изменение всей логики аутентификации клиента и сервера.

## 3. Риски

- Безопасность: вариант A оставляет реальное окно; вариант B закрывает отзыв, но вводит
  новый класс отказов — недоступность хранилища отзыва, и выбор между fail-open
  (безопасность) и fail-closed (доступность) является политикой, а не техническим дефолтом.
- Эксплуатация: очистка истекающих записей, метрики размера множества, поведение при
  перезапуске процесса при памятьном fallback — после перезапуска отзывы теряются.
- Миграции: вариант C требует схемы и миграции всех сценариев выдачи; вариант B — новый
  ключ в Redis без изменения схемы БД.
- UX: мгновенный отзыв на другой вкладке выглядит как «меня выкинуло»; офлайн-очередь
  начнёт получать отказ при отправке отложенных действий.
- Обратимость: A тривиально обратим; B обратим флагом, но отзытые токены уже не вернуть в
  срок; C практически необратим без миграции обратно.

## 4. Стоимость

- Инженерная сложность: A — нулевая; B — средняя (хранилище, проверка в зависимостях,
  тесты на каждый авторизованный путь, метрики); C — высокая (схема, ротация, полный
  пересмотр клиентской авторизации и офлайн-очереди).
- Драйверы затрат B: количество авторизованных эндпоинтов, объём операций выхода и
  смены роли, требования к наблюдаемости.
- Драйверы затрат C: миграция клиента, офлайн-сценарии, эксплуатация хранилища сессий.
- Денежные суммы, сроки, SLA: UNKNOWN — источника нет.

## 5. Рекомендация

Предложение (не решение): вариант B как целевое состояние, но вводить его только вместе с
явно утверждённой политикой при недоступности хранилища отзыва и только если владелец
считает окно в десятки минут неприемлемым для привилегированных ролей.

Явные предпосылки:

- Владелец отдельно отвечает, что важнее при сбое хранилища отзыва: доступность
  (fail-open с метрикой и алертом) или безопасность (fail-closed с отказом входа).
- Множество отзывов ограничено по TTL и очищается; значения идентификаторов токенов не
  попадают в логи и метки метрик.
- Проверка добавляется в единую точку авторизации, а не в отдельные хендлеры, иначе
  появятся обходные пути.
- Офлайн-очередь клиента обрабатывает отказ так же, как отказ по сроку действия токена.
- Существующий прецедент ADR-0028 (одноразовый билет с TTL) считается приемлемым образцом
  для варианта B.

## 6. Миграция/rollout (гипотетически, не выполняется)

Ничего не запускалось, схема не менялась, production не затрагивался.

1. Включить проверку в режиме наблюдения: писать решение, но не влиять на выдачу.
2. Проверить, что записи появляются на logout и при отзыве доступа, а множество
   ограничено и очищается.
3. Перевести в принудительный режим с утверждённой политикой сбоя.
4. Зафиксировать метрики: размер множества, доля проверок, ошибки хранилища.
- Откат: флаг проверки выключается, поведение возвращается к текущему (короткий TTL);
  накопленные записи отзыва остаются безвредными до истечения TTL.
- Стоп-условия: рост 5xx; заметное замедление авторизованных запросов; ошибки хранилища
  отзыва; появление идентификаторов токенов в логах.

## 7. Требуемое решение владельца

Вопрос: утверждается ли серверный отзыв выданных access-токенов (A — нет, риск с коротким
TTL принимается; B — blocklist с проверкой на каждом запросе; C — серверные сессии)? Если
B, то что считается приоритетом при недоступности хранилища отзыва и какой максимальный
срок жизни access-токена приемлем.

Что останется заблокированным без ответа: finding SEC-05 остаётся низким риском без плана;
«выйти со всех устройств» и мгновенный отзыв доступа сотрудника остаются невозможными, а
часть ролевых сценариев (отзыв доступа, logout на другом устройстве) не может быть
покрыта как «зелёная» при проверке C3.
