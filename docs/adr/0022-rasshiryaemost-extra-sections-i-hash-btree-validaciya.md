# ADR 0022 — Расширяемость extra_sections и валидация Hash/B-Tree без БД

**Дата:** 2026-09-03
**Статус:** принят
**Tier:** T2 — reestr-kompetencii-udgu

## Контекст
R24: «у УдГУ больше типов данных, указанные — просто примеры» — перечень кафедры/заделы/миссия/оборудование/патенты/услуги/люди не исчерпывающий. Одновременно нужна детерминированная дедупликация внутри выгрузки и проверка диапазонов дат/годов (R22), но MVP без БД/миграций — индексы Postgres недоступны. Терминология проекта вводит `00_опись`, `raw_refs`, `udgu_import.json`, `Wave1/Wave2`, «реестр потенциала УР» как целевой реестр.

## Решение
- **Расширяемость:** инструкция расширения — добавить `08_мой_тип/` + лист по шаблону `08_...` (копия структуры заголовков/валидации); пайплайн подхватывает без изменения кода — нормализованное имя листа/папки, неизвестное — в отчёт и в `raw_refs`/`extra_sections`. Лист `99_raw_опись` фиксирует соответствие «файл в raw/ → сущность/строка».
- **Валидация:** Hash-логика для дедупликации по ключу `(тип + нормализованное название + год)` — детект дублей оборудования/РИД внутри ZIP без БД-индекса. B-Tree-логика для диапазонов (годы `1900–2026`, даты, `trl 1–9`) — проверка упорядоченности/границ как кодовая валидация, а не индекс БД. Оба — чистые функции в пайплайне.

## Почему (с отвергнутыми)
- **Жёсткие 7 листов без расширения — отвергнуто:** ломается при каждом новом типе УдГУ, требует релиза пайплайна.
- **Расширение через миграцию схемы/БД — отвергнуто:** противоречит офлайн-CLI без БД (ADR-0020) и Wave2 без дедлайна.
- **Дедупликация только в БД (Hash/B-Tree индексы Postgres) — отвергнута:** БД нет в MVP, а R01 требует staging-изоляцию; Hash-индекс для точного поиска и B-Tree для диапазонов применяются как логика, не как `CREATE INDEX`.
- **Без дедупликации/без проверки диапазонов — отвергнуто:** копятся дубли «Станок X 2021» в разных кафедрах и невалидные года.
- **Криптографический Hash / внешняя библиотека — отвергнуто:** достаточно нормализованного ключа, коллизии сознательно допустимы на масштабе 10–1000 строк.

## Последствия
- Плюс: Wave2 (миссия/фронтир/заделы/услуги + любые `08_...`) не ломает шаблон и пайплайн; сырые файлы не теряются — попадают в `raw_refs` и в метрику отчёта «заполненность по разделам %»; термины `Wave1/Wave2`, `00_опись`, `реестр потенциала УР` фиксируют границы MVP.
- Минус: Hash на нормализованном названии чувствителен к опечаткам — «Станок X» vs «Станок Х» (лат.) даст дубль, mitigated отчётом дублей; B-Tree-проверка — только валидация, не ускоряет поиск (индекса нет).
- Цена: `extra_sections` — слаботипизированный мешок, маппинг на `organizations.competencies` для новых типов — только документацией до отдельного тикета заливки.
