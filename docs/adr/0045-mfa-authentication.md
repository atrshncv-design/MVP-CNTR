# ADR 0045: MFA для ролей и операторов

Статус: proposed — решение владельца требуется

Тема: вводить ли многофакторную аутентификацию и для кого. Решение не принято, код
аутентификации не менялся, учётные записи не создавались.

## 1. Текущее состояние

Подтверждено:

- MFA/2FA в бэкенде отсутствует: 0 совпадений `totp|otp|mfa|2fa` по
  `technozrelost-backend/app` — finding SEC-04 в
  `docs/audit/2026-09-21-production/09-final/findings.json`,
  `docs/audit/2026-09-21-production/05-security/security.md`.
- Восстановление доступа — только ручное, силами персонала:
  `POST /users/{user_id}/reset-password` (`technozrelost-backend/app/api/v1/users.py`),
  с отзывом сессий цели и записью аудита. Самовосстановление и подтверждение по почте не
  реализованы, SMTP не используется (там же).
- Аутентификация — JWT HS256 с коротким TTL access и ротацией refresh; refresh отзывается
  атомарно вместе с семейством при повторном использовании (ADR-0029,
  `technozrelost-backend/app/api/v1/auth.py`).
- Саморегистрация ограничена allowlist непривилегированных ролей; привилегированные роли
  (`auditor`, `regulating_organization`, `ugt_expert`, `investor`, `cntr_admin`,
  `cntr_manager`) перечислены в `PRIVILEGED_ROLE_SLUGS`
  (`technozrelost-backend/app/core/deps.py`) и через allowlist не проходят (ADR-0030).
- Аудит квалифицирует отсутствие MFA как продуктовую рекомендацию, а не дефект, и
  оставляет решение владельцу (SEC-04).

UNKNOWN (не утверждается):

- Готовность сотрудников Центра использовать TOTP-приложения или аппаратные ключи;
- наличие у владельца требований регулятора по MFA для привилегированных ролей;
- допустимость ли физических носителей и порядок их выдачи.

## 2. Варианты

- **A. Оставить однофакторную аутентификацию, риск принять формально.** Последствия:
  нулевая дополнительная работа и нулевой риск блокировок, но привилегированные роли
  защищены только паролем, а компрометация пароля даёт доступ без второго барьера.
- **B. TOTP для привилегированных и операторских ролей, остальные — как сейчас.**
  Последствия: заметно снижает риск по ценке нового экрана подтверждения и процедуры
  сброса; требует безопасного хранения секрета, что упирается в недоказанное
  шифрование at-rest (finding DB-04).
- **C. TOTP для всех + управляемые коды восстановления.** Последствия: единый
  контроль для всего контура, но выше стоимость поддержки, больше состояний в интерфейсе и
  новая процедура выдачи кодов, доставка которых в платформе не автоматизирована (почта не
  используется).

## 3. Риски

- Безопасность: MFA снижает риск компрометации пароля, но добавляет новый —
  компрометацию канала подтверждения; хранение TOTP-секретов в открытом виде означает, что
  защита держится на уровне приложения, а не СУБД.
- Эксплуатация: главный операционный риск — блокировка единственного сотрудника Центра без
  второго фактора; процедура «аварийного входа» должна существовать до включения MFA, и она
  не может опираться на самодельные учётные записи.
- UX: дополнительный шаг при входе для сотрудников, риск недовольства пользователей и
  ошибок при настройке приложения; нужен сценарий «забыл код», не переводящий пользователя
  в тупик.
- Обратимость: отключение MFA возможно только вместе с удалением секретов; секрет,
  попавший в бэкап, остаётся в бэкапе (точка из DB-04).
- ПДн: усиление аутентификации уменьшает риск доступа к персональным данным, но не заменяет
  политику доступа к ним (ADR-0043, ADR-0044).

## 4. Стоимость

- Инженерная сложность: A — нулевая; B — средняя (эндпоинты включения и подтверждения,
  хранение секрета, административный сброс, фронтенд-экраны, тесты); C — высокая
  (коды восстановления, несколько устройств, аудит событий, политика сброса).
- Драйверы затрат варианта B: шифрование at-rest для новых секретов, процедура сброса,
  наблюдаемость попыток подтверждения.
- Драйверы затрат варианта C: дополнительно — доставка кодов восстановления и хранение их
  состояния.
- Денежные суммы, стоимость лицензий, сроки и SLA: UNKNOWN — источника нет; стоимость
  конкретного поставщика не приводится.

## 5. Рекомендация

Предложение (не решение): вариант B — TOTP для привилегированных ролей и операторов Центра,
с сохранением текущей ручной процедуры сброса как единственного пути восстановления до
момента, пока не появится управляемое восстановление. Если сотрудники не готовы использовать
TOTP-приложения, альтернативой тому же уровню риска является аппаратный ключ, и это отдельный
вопрос владельца.

Явные предпосылки:

- У сотрудников есть доступ к телефону или аппаратному носителю; если нет, предложение B
  нереализуемо в текущем виде.
- Процедура аварийного входа описана до включения MFA, и в ней нет создания новых учётных
  записей вне реестра пользователей.
- Секреты TOTP не попадают в логи, отчёты и выгрузки; хранение — по правилам раздела
  at-rest (DB-04), даже если текущий статус at-rest UNKNOWN.
- Ролевые сценарии C3 остаются `BLOCKED` до выдачи безопасных аккаунтов, поэтому
  обязательная проверка входа возможна только после их получения (T19).

## 6. Миграция/rollout (гипотетически, не выполняется)

Ничего не запускалось; учётные записи не создавались, production не затрагивался.

1. Контур включения: необязательный для всех, обязательный — только для перечисленных
   владельцем ролей; переключатель — конфигурация, а не правка кода на проде.
2. Обратная совместимость: пользователь без второго фактора продолжает входить, пока
   владелец не включит требование для его роли.
3. Окноgrace: период, в котором привилегированная роль может войти без второго фактора,
   с фиксацией в журнале; длительность — решение владельца.
4. Процедура сброса: описание до включения обязательности, с отзывом сессий и аудитом,
   по образцу существующего `reset-password`.
5. Наблюдаемость: счётчики успешных/неуспешных подтверждений без значений секретов.
- Откат: выключить требование второго фактора для роли; уже выпущенные секреты отозвать.
- Стоп-условия: блокировка сотрудника без работающей процедуры восстановления; появление
  секретов или кодов в логах/выгрузках; рост 5xx или заметное замедление входа.

## 7. Требуемое решение владельца

Вопрос: вводится ли второй фактор (A — нет, риск принять формально; B — TOTP для
привилегированных и операторских ролей; C — для всех с кодами восстановления)? Если да, то
какие роли считаются привилегированными для MFA, каков срок окна настройки и кто имеет
право сбрасывать второй фактор.

Что останется заблокированным без ответа: finding SEC-04 остаётся рекомендацией без плана;
компрометация пароля привилегированной роли даёт полный доступ; проверка «вход с MFA» не
попадёт в матрицу ролевых сценариев, а при выдаче безопасных аккаунтов (T19) эта часть
ролевой матрицы останется недоказанной.
