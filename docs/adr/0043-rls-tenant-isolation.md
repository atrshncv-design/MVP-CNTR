# ADR 0043: PostgreSQL Row-Level Security и tenant-изоляция

Статус: proposed — решение владельца требуется

Тема: перевести изоляцию данных с application-level на уровень СУБД или оставить её
как есть. Решение не принято, код не менялся, DDL не выполнялся.

## 1. Текущее состояние

Подтверждено:

- Колонки `tenant_id` в модели нет; `CREATE POLICY` / `ENABLE ROW LEVEL SECURITY` в
  репозитории не встречаются (0 совпадений) — finding DB-02 в
  `docs/audit/2026-09-21-production/09-final/findings.json`, обзор модели:
  `docs/audit/2026-09-21-production/04-database/db-model.md`.
- Изоляция обеспечивается исключительно на уровне приложения:
  `require_role` / `has_role` (`technozrelost-backend/app/core/deps.py`),
  `can_access_project` / `require_project_access`
  (`technozrelost-backend/app/api/v1/projects.py`), проверка приглашений и админства
  проекта (`technozrelost-backend/app/api/v1/invites.py`).
- Привилегированные роли отделены от саморегистрируемых константами
  `PRIVILEGED_ROLE_SLUGS` и `SELF_REGISTER_ALLOWED_SLUGS`
  (`technozrelost-backend/app/core/deps.py`); привилегированные не проходят allowlist
  саморегистрации (ADR-0030, миграция
  `technozrelost-backend/alembic/versions/0033_revoke_self_registered_privileges.py`).
- Границы AI-контуров (`tuno` / `kaba`) тоже application-level: предикат `contour` и
  `CHECK (contour IN ('tuno','kaba'))`, per-contour частичные индексы; RLS отсутствует —
  `docs/audit/2026-09-21-production/07-ai/ai.md` и
  `docs/audit/2026-09-21-production/07-ai/ai-registry.json`.
- Каталог production-БД: 41 public-таблица (39 ORM + `alembic_version` +
  `db_migration_log`), grants только основной роли, отдельной read-only роли нет —
  finding DB-01.

UNKNOWN (не проверялось и не утверждается здесь):

- Авторизованная runtime-проверка ролевых сценариев: до выдачи безопасных тестовых
  аккаунтов статус `BLOCKED` (C3, R19, T19).
- Существует ли бизнес-требование к настоящей мультиарендности (несколько независимых
  организаций-tenant с общей схемой и общими запросами). В текущей модели роли и проекты
  принадлежат Центру, а не внешнему tenant — это продуктовое допущение, а не доказанный
  факт владения данными.

## 2. Варианты

- **A. Оставить application-level изоляцию** и зафиксировать её как осознанное решение
  владельца. Последствия: миграций нет, текущие регрессионные тесты ролей остаются
  единственной защитой; при росте числа ролей и запросов риск пропущенной проверки
  переносится целиком на дисциплину кода и ревью.
- **B. `tenant_id` + RLS с транзакционным контекстом** (`SET LOCAL app.<tenant>`,
  `FORCE ROW LEVEL SECURITY`, отдельная непривилегированная роль приложения). Последствия:
  двойной источник правды (код и политика) либо полный перенос прав в политику; каждый новый
  запрос и тестовая фикстура должны задавать контекст tenant; риск «тихого» обхода политики
  при пустом контексте (нужен fail-closed на отсутствии контекста).
- **C. Схема или база на организацию** (отдельная схема/БД на tenant). Последствия:
  изоляция максимальна, но эксплуатация (миграции, бэкап, restore, pooled-аналитика)
  усложняется на порядок, а текущая численность контуров этого не требует.

## 3. Риски

- Безопасность: главный риск варианта A — ошибка в application-level фильтре
  (пропущенный `where`) даёт утечку строк без следа в БД; вариант B закрывает класс
  ошибок на уровне СУБД, но вводит новый класс — неверный/пустой контекст tenant.
- Эксплуатация: RLS требует дисциплины с ролями и `FORCE ROW LEVEL SECURITY`, иначе
  владелец таблицы (миграции alembic) обходит политику; read-путь на реплике
  (`get_read_db`, `technozrelost-backend/app/core/database.py`) обязан применять ту же
  политику, иначе чтение и запись разойдутся по видимости.
- Миграции: вариант B требует миграции всех 39 ORM-таблиц и пересмотра всех
  `SELECT`; откат политики возможен, откат уже добавленного `tenant_id` — нет.
- UX: при включении RLS пользователь может увидеть «пустой» список, если контекст не
  проставлен, — это выглядит как потеря данных, а не как отказ доступа.
- Обратимость: A обратим тривиально, B обратим только флагом политики при сохранении
  `tenant_id`, C практически необратим без конвертации данных.

## 4. Стоимость

- Инженерная сложность: A — нулевая дополнительная работа; B — высокая (схема, запросы,
  фикстуры, тесты, read-путь); C — очень высокая (эксплуатационная машинерия вокруг
  нескольких схем/БД).
- Драйверы затрат варианта B: объём ORM-моделей, количество эндпоинтов, размер тестовой
  сюиты, необходимость отдельной роли приложения в БД.
- Драйверы затрат варианта C: бэкап/restore на N баз, покрытие миграциями, мониторинг.
- Денежные суммы, сроки, SLA и коммерческие оценки: UNKNOWN — источника нет, ничего не
  придумывается.

## 5. Рекомендация

Предложение (не решение): выбрать вариант A на текущем этапе и зафиксировать
application-level изоляцию как осознанную позицию, а вариант B пересматривать только при
одном из двух триггеров: (1) владелец вводит настоящую мультиарендность в состав MVP,
(2) регулятор или внутренний аудит требует изоляции на уровне СУБД.

Явные предпосылки, без которых предложение недействительно:

- Платформа остаётся контуром Центра: пользователи, проекты и реестры не разделяются по
  внешним tenant.
- Регрессионные тесты «роль + владение + приглашение» и IDOR/BOLA остаются обязательными
  перед любым изменением модели доступа (T18; runtime — T19).
- Решения о составе ролей и публичности реестров (ADR-0049, ADR-0051) принимаются
  владельцем независимо от этого ADR.

Если предпосылка первая неверна, вариант A становится риском, а не решением: тогда нужен
вариант B отдельным тикетом до приёмки C3.

## 6. Миграция/rollout (гипотетически, не выполняется)

Ничего из перечисленного не запускалось; команды применения намеренно не приводятся,
любое касание схемы или production — только по отдельному разрешению владельца.

1. Схема: добавить nullable `tenant_id` и индексы, поведение приложения не менять.
2. Обратная совместимость: старый код продолжает работать, потому что политик ещё нет.
3. Заполнение и проверка: backfill по существующим правилам владения, сверка числа строк.
4. Политики: создать политики в режиме «разрешающая заглушка» → перевести в фильтрующую,
   с обязательным fail-closed при отсутствии контекста.
5. Роль приложения: перевести соединения на непривилегированную роль + `FORCE ROW LEVEL
   SECURITY`; проверить, что миграции alembic идут отдельной ролью.
6. Read-путь: убедиться, что реплика применяет те же политики.
7. Contract-шаг в отдельном релизе: убрать дублирующую application-level проверку, если
   решено, что правда в политике.
- Откат: отключить политики и `FORCE`, вернуть application-level фильтры; `tenant_id`
  остаётся (безвредная колонка), его удаление — отдельная задача.
- Стоп-условия: любая строка чужого tenant в выдаче тестов; рост 5xx; замедление
  read-пути; ошибки миграций; расхождение числа строк после backfill.

## 7. Требуемое решение владельца

Вопрос: какой вариант изоляции данных утверждается для платформы?

- A — оставить application-level (рекомендуемое предложение, предпосылки в §5);
- B — ввести `tenant_id` + RLS (отдельный тикет: схема, запросы, тесты, роли);
- C — схема/БД на организацию (отдельный проект с новой эксплуатацией).

Что останется заблокированным без ответа: finding DB-02 остаётся «решение не принято»;
новая функциональность будет добавляться без `tenant_id`, что делает последующий переход к
варианту B дороже; пункт C4 (топология и риски) не закрывается по этой части; владелец
не получает основы для решения, считать ли изоляцию риском, принятым или закрытым.
