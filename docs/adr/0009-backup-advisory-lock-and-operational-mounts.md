# ADR 0009: Advisory lock для backup (backup-lock.py) и operational mounts вместо запекания в образ

**Tier:** T2 — correctness/concurrency, reversal = гонки бэкапов и невоспроизводимые артефакты
**Date:** 2026-08-28
**Status:** accepted

## Title
Сериализация бэкапов через Postgres advisory lock и хранение артефактов на operational mounts

## Context
К концу M0 `backup.sh` запускается по расписанию внутри прод-стека (cron/таймер), а API работает в 2 репликах за nginx. Без координации два триггера (таймер + ручной вызов, перезапуск контейнера, наложение расписаний после простоя) могут запустить `pg_basebackup` параллельно — конкуренция за IO, частичные артефакты, ложный маркер «успеха». Файловый `flock` внутри одного контейнера не виден второму, а бэкапы/WAL, запечённые в образ, теряют смысл: образ иммутабелен, данные — нет.

## Decision
- Ввести `backup-lock.py` — тонкую обёртку вокруг `pg_try_advisory_lock(key)` с выделенным ключом. Захват — в начале `backup.sh`, освобождение — гарантированно в конце (trap/exit). Неудача захвата → немедленный выход с ненулевым кодом и без перезаписи маркера успеха; алертер видит устаревший маркер.
- Координация через БД, а не через файловую систему: БД — единственная общая точка всех реплик/контейнеров стека, переживает рестарт отдельного контейнера.
- Артефакты (base-backup, WAL-архив, маркеры возраста) — только на named volumes / host mounts, монтируемых в runtime. Скрипты (`backup.sh`, `backup-lock.py`, wal-sidecar) запечены в образ, данные — никогда. Pre-migration бэкап пишет image-run marker, а не блокирует деплой.

## Consequences
**Положительные:** параллельные запуски сериализуются независимо от количества API-реплик и sidecar-ов; гонка превращается в наблюдаемый отказ, а не в тихую порчу; бэкапы переживают пересборку образов и `docker compose down`; деплой не висит на длительном бэкапе.

**Отрицательные / цена:** зависимость от доступности primary — при недоступности БД lock не взять, бэкап пропускается (это правильно, но требует алерта по маркеру); нужен выделенный ключ advisory lock и договорённость не пересекать его с другими использованиями; operational mounts требуют lifecycle-управления (бэкап томов, права `postgres:postgres`, 0600 для passfile) и не клонируются вместе с образом.

**Что отвергли и почему:**
- *`flock` / pidfile на volume* — отвергнуто: работает только внутри одного mount namespace; при двух репликах API каждая видит свой файл, гонка остаётся.
- *Cron single-instance через systemd/host* — отвергнуто: прод-стек — набор контейнеров, хостовый cron вне Compose ломает принцип «одна команда поднимает весь контур» и не тестируется локально.
- *Запекание бэкапов/WAL в образ или layer* — отвергнуто: образ раздувается, артефакты не обновляются без пересборки, теряется разделение «код vs данные»; восстановление требовало бы выковыривания данных из истории слоёв.
- *Блокирующий pre-migration бэкап без маркера* — отвергнуто: деплой с долгим `pg_basebackup` выглядит зависшим и упирается в health-gate timeout; non-blocking маркер честнее.
