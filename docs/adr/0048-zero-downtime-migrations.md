# ADR 0048: Zero-downtime deployment и expand/contract миграции

Статус: proposed — решение владельца требуется

Тема: как изменяется схема данных при выкатке приложения. Решение не принято, миграции не
создавались и не выполнялись, production не затрагивался.

## 1. Текущее состояние

Подтверждено:

- Миграции только через Alembic, линейная цепочка ревизий, каждая с `upgrade` и
  `downgrade`; текущий head — `0037_status_checks` (каталог
  `technozrelost-backend/alembic/versions/`). Применённый head в production совпадает с
  файловым — `public.alembic_version = 0037` (finding DB-01,
  `docs/audit/2026-09-21-production/09-final/findings.json`).
- Миграции применяются автоматически при старте контейнера:
  `alembic upgrade head` под advisory-lock в
  `technozrelost-backend/infra/backend-entrypoint.sh`; при `BACKUP_BEFORE_MIGRATIONS=1`
  (дефолт в production-профиле) сначала выполняется
  `technozrelost-backend/infra/backup-lock.py`, и занятый lock останавливает миграции
  fail-closed (ADR-0009, ADR-0032).
- Модель — 39 ORM-таблиц плюс служебные `alembic_version` и `db_migration_log`
  (тот же DB-01); правило проекта: схема меняется только Alembic, SQL — только через ORM
  или безопасной параметризацией.
- Покрытие изменений — линейное, без параллельных веток; значит, два разных приложения
  против одной схемы возможны только если старая версия продолжает работать на новой схеме.
- Релизная дисциплина уже описана: поставка тремя пакетами с gating (ADR-0039), приёмка
  пакетами, а не релизом целиком.
- Статус контура: один backend, один worker (ADR-0015), single-node (ADR-0035) — то есть
  «нулевой простоя» в текущей топологии ограничен самой топологией.

UNKNOWN (не утверждается):

- Фактические длительности блокировок при текущих миграциях — не измерялись.
- Потребность в длительных backfill-операциях при росте объёма данных — не измерена.
- Допустимо ли окно недоступности в текущем SLA: формального SLA нет (ADR-0035).

## 2. Варианты

- **A. Текущая практика: миграция при старте контейнера, при несовместимости — окно
  недоступности или откат версии.** Последствия: просто и предсказуемо, но «откат версии»
  после необратимого шага миграции (удалённая колонка, преобразованные данные) означает
  простой и потерю данных.
- **B. Expand/contract как дисциплина** для рискованных изменений: расширение
  (nullable-колонка или новая таблица) → бэкафилл → двойная запись/чтение в новом виде →
  переключение → сокращение в отдельном релизе. Последствия: старый и новый код работают
  одновременно, изменение занимает два релиза, но откат после первого шага безопасен.
- **C. Онлайн-инструменты для тяжёлых операций** (пересборка индексов без блокировки,
  добавление `NOT NULL` через проверочное ограничение с валидацией) плюс автоматический
  откат. Последствия: почти нулевое окно недоступности, но выше требования к
  квалификации, к проверке ограничений на больших таблицах и к дисковому запасу.

## 3. Риски

- Миграции: главный риск варианта B — «забытая вторая половина»: расширение без сокращения
  оставляет мусор в схеме, а сокращение раньше времени ломает старую версию. Нужна
  явная проверка, что контрактный шаг не попадает в тот же релиз.
- Эксплуатация: автоматическая миграция при старте контейнера означает, что ошибка
  миграции останавливает выкатку; это осознанно (fail-closed) и требует процедуры
  «миграция не прошла — что делаем».
- Безопасность/данные: бэкап перед миграцией обязателен; он уже встроен, но его
  пригодность не доказана репетицией restore (OPS-03), то есть откат может опираться на
  непроверенную копию.
- UX: при перезапуске контейнера во время миграции пользователь видит недоступность; в
  single-node топологии окно равно времени миграции плюс рестарт.
- Обратимость: A обратима до необратимого шага; B — на каждом промежуточном шаге; C —
  обратимость ограничена самим инструментом и наличием свободного места под пересборку.

## 4. Стоимость

- Инженерная сложность: A — низкая (текущее состояние); B — средняя (правило, чек-лист
  ревью, тесты на совместимость старой и новой версии, дисциплина двух релизов); C —
  высокая (отдельные инструменты, проверка ограничений, запас по диску).
- Драйверы затрат B: число рискованных изменений и релизный цикл; основная нагрузка —
  процессная, а не инструментальная.
- Драйверы затрат C: квалификация DBA/разработчика, время валидации ограничений.
- Денежные суммы, сроки, SLA: UNKNOWN — источника нет.

## 5. Рекомендация

Предложение (не решение): вариант B как обязательная дисциплина для изменений, затрагивающих
существующие данные или поля, читаемых старой версией; вариант A остаётся допустимым для
мелких обратимо-совместимых изменений; вариант C — только для отдельных тяжёлых операций по
результатам измерений, которых пока нет.

Явные предпосылки:

- Миграции остаются только Alembic с `upgrade` и `downgrade`; новые инструменты не заменяют
  цепочку ревизий.
- Бэкап перед миграцией и блокировка занятым lock сохраняются (ADR-0009, ADR-0032).
- Наличие доказанного restore (T17) — предпосылка для заявления «откат возможен»; без неё
  формулировка про откат условна.
- Ветка и релизная дисциплина (ADR-0039) позволяют делать два шага вместо одного.

## 6. Миграция/rollout (гипотетически, не выполняется)

Ничего не выполнялось; команды применения не приводятся, любые миграции возможны только по
отдельному разрешению владельца.

1. Зафиксировать правило в чек-листе ревью миграций: рискованное изменение разбивается на
   expand и contract, они не попадают в один релиз.
2. Expand: добавить nullable-структуру, ничего не менять в поведении; этап обратим
   удалением добавленного элемента.
3. Бэкафилл отдельными порциями с ограничением по времени, с проверкой числа строк.
4. Двойная запись или чтение в новом виде; старая версия приложения продолжает работать.
5. Переключение на новое поведение; наблюдение за ошибками и латентностью.
6. Contract: удаление старого элемента в отдельном релизе, после подтверждения, что старая
   версия больше не используется.
- Откат: на шагах 1–4 — откат кода без потери данных; на шаге 5 — откат кода при сохранении
  обеих форм данных; после шага 6 откат означает восстановление из копии, поэтому шаг 6
  требует отдельного подтверждения.
- Стоп-условия: превышение допустимого времени блокировки (значение утверждает владелец);
  ошибки миграции; расхождение числа строк после бэкафилла; рост 5xx после переключения;
  отсутствие свежего бэкапа перед рискованным шагом.

## 7. Требуемое решение владельца

Вопрос: какая политика миграций утверждается — A (текущая практика с окном недоступности),
B (expand/contract по умолчанию) или C (онлайн-инструменты для тяжёлых операций)? И какое
допустимое окно недоступности при выкатке считается приемлемым, после которого применяется
B.

Что останется заблокированным без ответа: каждое рискованное изменение схемы решается
заново и по-разному; откат после необратимого шага остаётся восстановлением из копии без
измеренного RTO; релизная дисциплина ADR-0039 не получает правила для изменений данных,
а не только кода.
