# ADR 0007: HBA least-privilege на фиксированных подсетях и dev-only pg_hba.dev.conf

**Tier:** T2 — load-bearing, reversal = пересборка сети и пересоздание БД-контура
**Date:** 2026-08-28
**Status:** accepted

## Title
Фиксированные Docker-подсети 172.30.0.0/24 (prod) / 172.31.0.0/24 (dev) и раздельные HBA-файлы с least-privilege

## Context
К моменту G1 PostgreSQL работал в Docker Compose с primary/replica. Изначальный HBA допускал широкие CIDR и содержал `trust` для local — удобно для разработки, но несовместимо с B2G-контуром с ПДн и конфиденциальными НИОКР-документами. Любой контейнер в default bridge мог получить доступ, а dev-подсеть и prod-подсеть не различались, что делало проверку HBA невоспроизводимой между окружениями. Требовалось закрыть поверхность так, чтобы правило «разрешено только явно перечисленному» проверялось контракт-тестами, а не надеждой.

## Decision
- Зафиксировать подсети на уровне Compose IPAM: `172.30.0.0/24` — prod, `172.31.0.0/24` — dev. Подсеть становится частью контракта, а не побочным эффектом Docker.
- Разделить HBA: `pg_hba.conf` — единственный файл, монтируемый в prod (hostssl/scram-sha-256, явные пользователи `app`, `replicator`, `postgres` по конкретным CIDR); `pg_hba.dev.conf` — только в dev, допускает `172.31.0.0/24` и ограниченный gateway Docker Desktop `192.168.65.0/24` для хостовой разработки.
- Убрать `trust` и `0.0.0.0/0`, убрать передачу пароля через argv (`:'slot'`), пароль только через env/passfile; HBA монтируется как operational mount, а не запекается в образ.

## Consequences
**Положительные:** prod-HBA верифицируется статически (contract-тест на отсутствие trust/0.0.0.0, на наличие только 172.30), dev-удобство не заражает prod; смена подсети ломает деплой явно, а не тихо расширяет доступ; поверхность для горизонтального перемещения внутри хоста сведена к перечисленным CIDR.

**Отрицательные / цена:** любое изменение сети требует `recreate` контейнеров и синхронизации HBA с Compose — операционная связность; dev-контейнер с устаревшим HBA остаётся unhealthy до пересоздания; поддержка двух файлов удваивает место для дрейфа — нужен guard-тест на паритет правил; жёсткая привязка к 172.30/172.31 исключает произвольные оверлеи без правки ADR и контрактов.

**Что отвергли и почему:**
- *Один HBA на все окружения* — отвергнут: dev-послабления неизбежно уезжают в прод, контракт «prod строже dev» недоказуем.
- *Динамический HBA / host all all 0.0.0.0/0 md5* — отвергнут: проще в эксплуатации, но нарушает least-privilege и делает аудит 152-ФЗ формальным; любая новая сеть получает доступ по умолчанию.
- *Запекание HBA в образ* — отвергнуто: правило доступа становится неизменяемым без пересборки образа, теряется возможность ротации без релиза; mount позволяет менять политику без смены артефакта.
