# ADR 0044: Soft delete, retention и восстановление удалённых данных

Статус: proposed — решение владельца требуется

Тема: что происходит с удалёнными бизнес-данными и данными с ПДн — жёсткое удаление,
soft delete с окном восстановления или архивирование. Решение не принято, схема не
менялась, миграции не выполнялись.

## 1. Текущее состояние

Подтверждено:

- Колонок `is_deleted` / `deleted_at` нет ни в одной таблице репозитория (0 совпадений) —
  finding DB-06 в `docs/audit/2026-09-21-production/09-final/findings.json`; обзор
  модели: `docs/audit/2026-09-21-production/04-database/db-model.md`.
- Удаление проекта — жёсткое (`delete_project`, `technozrelost-backend/app/api/v1/projects.py`),
  рядом есть отдельная архивная операция (`archive_project`, тот же файл); интерфейса
  восстановления удалённого нет.
- `audit_trail` покрывает действия с проектами (`project_id` / `action` / `details`) и не
  является журналом lifecycle сущностей — там же DB-06.
- Удаление и архивирование разрешено не всем: привилегированные и админские роли отделены
  константами `PRIVILEGED_ROLE_SLUGS` (`technozrelost-backend/app/core/deps.py`).
- Политика хранения персональных данных в продукте не зафиксирована: аудит выносит
  soft-delete/retention в backlog после решения владельца (DB-06, DB-04,
  `docs/audit/2026-09-21-production/05-security/README.md`).
- Локальные копии ограничены параметром `BACKUP_KEEP`, offsite-контур имеет собственную
  политику retention — `docs/audit/2026-09-21-production/08-operations/operations.md`,
  ADR-0008, ADR-0009. Это политика копий, а не политика удаления данных в БД.

UNKNOWN (не утверждается):

- Какие именно поля сущностей являются персональными данными и какие сроки хранения
  применимы к каждому классу. Подтверждено только наличие `User.email`
  (`technozrelost-backend/app/db/models.py`); состав ПДн в карточках проектов и
  организаций в этом прогоне не инвентаризировался.
- Существует ли требование субъекта ПДн на удаление своих данных и кто его исполняет
  сегодня (процесс не описан).

## 2. Варианты

- **A. Жёсткое удаление + журнал действий как есть.** Последствия: просто и дёшево, но
  ошибка удаления необратима, а «восстановление» возможно только из бэкапа, то есть с
  потерей всех более поздних изменений.
- **B. Soft delete для всех бизнес-сущностей** (`deleted_at` + окно восстановления +
  фоновая очистка). Последствия: обратимость и аудит, но каждый `SELECT` обязан фильтровать
  удалённое, а пропущенный фильтр — утечка удалённых данных в витрине, поиске и выдаче
  matching.
- **C. Ограниченный soft delete** — только для сущностей с персональными данными
  (пользователи, организации, проекты), техника и производные записи удаляются жёстко.
  Последствия: меньше изменений в запросах, но требуется предварительный перечень
  «ПДн-сущностей», который является продуктовым решением, а не техническим.

## 3. Риски

- Безопасность/ПДн: риск двусторонний, и нормативная рамка в этом прогоне не установлена.
  Удержание удалённых персональных данных дольше фактически необходимого срока — риск,
  а не автоматически установленный факт нарушения: какие сроки хранения применимы к
  каждому классу данных, должен подтвердить владелец вместе с юристом, иначе обосновать
  окно хранения нечем (см. §1 UNKNOWN). Обратная сторона — без soft delete
  восстановление возможно только из копии, где удалённые данные вернутся целиком.
- Эксплуатация: фоновая очистка удалённых строк влияет на бэкап и restore (архив будет
  содержать удалённое до отработки очистки) и на `pg_dump`/replay.
- Миграции: добавление `deleted_at` — дешёвая операция, но обратимость зависит от
  обратной совместимости старого кода; удаление колонки в следующем релизе.
- UX: «удалено» должно быть видно и восстановимо авторизованному пользователю, иначе
  пользователь сообщает об ошибке там, где удаление было законным; корзина в интерфейсе
  меняет привычные сценарии.
- Обратимость: вариант A необратим в принципе, B/C обратимы в пределах окна хранения, но
  после отработки очистки — нет.

## 4. Стоимость

- Инженерная сложность: A — без изменений; C — средняя (несколько сущностей, фильтры в
  выборках, индексы, тесты на каждую точку чтения); B — высокая (те же работы для всех
  таблиц плюс фоновая очистка и админский интерфейс восстановления).
- Драйверы затрат вариантов B/C: количество эндпоинтов чтения (витрина, поиск, matching,
  выгрузки), размер тестовой сюиты, необходимость фоновой задачи и её наблюдаемости.
- Драйверы затрат варианта A: риск, который не имеет цены в трудозатратах, но имеет цену
  инцидента — она не оценена.
- Денежные суммы, сроки, SLA и оценки хранения: UNKNOWN — источника нет.

## 5. Рекомендация

Предложение (не решение): рассмотреть вариант C — ограниченный soft delete для сущностей с
персональными данными, с явным перечнем сущностей и окном хранения, утверждённым владельцем,
и с обязательным запретом показа удалённых данных в витрине, поиске и подбору.

Явные предпосылки:

- Владелец может назвать перечень ПДн-сущностей и допустимое окно хранения; без этого
  предложение не реализуемо.
- Восстановление выполняет авторизованная роль (не владелец записи) и фиксируется в
  `audit_trail`.
- Перед включением soft delete точки чтения (витрина, поиск, matching, выгрузка) имеют
  regression-тесты, иначе фильтр «проверяется» только вручную.

Если владелец считает, что жёсткое удаление допустимо и цена ошибки приемлема, вариант A
остаётся корректным, и тогда DB-06 закрывается формулировкой «риск принят».

## 6. Миграция/rollout (гипотетически, не выполняется)

Ничего не запускалось; команды применения не приводятся, касание схемы возможно только по
отдельному разрешению владельца.

1. Expand: nullable-колонка `deleted_at` и индексы, поведение не меняется — этап полностью
   обратим.
2. Обратная совместимость: старый код читает все строки, новые ничего не скрывают.
3. Включение фильтра по одной сущности, начиная с наименее читаемой; на каждый шаг —
   regression-тест «удалённая строка не видна в <точке чтения>».
4. Ручное удаление переводится на soft delete; переход обратим переключением флага.
5. Фоновая очистка старше окна хранения — только после отдельного решения и проверки бэкапа.
6. Появление интерфейса восстановления — отдельным тикетом.
- Откат: выключить фильтр и вернуть жёсткое удаление (до появления очистки откат полный;
  после отработки очистки удалённые данные не вернуть).
- Стоп-условия: удалённая строка в витрине/поиске/выдаче; рост 5xx; заметное замедление
  выборок; ошибка фоновой очистки; потеря связи «удаление → запись в журнале».

## 7. Требуемое решение владельца

Вопрос: какая политика удаления утверждается — A (жёсткое удаление как сейчас), B (soft
delete для всех бизнес-сущностей) или C (soft delete только для ПДн-сущностей)? И в
качестве сопутствующих решений: перечень ПДн-сущностей, окно хранения (вместе с
ссылкой на подтверждённые владельцем и юристом применимые сроки — в этом прогоне они
не установлены), кто может восстанавливать, нужен ли пользовательский запрос на удаление
своих данных.

Что останется заблокированным без ответа: finding DB-06 остаётся открытым; новые таблицы
с персональными данными будут добавляться без `deleted_at`, и переход на обратимое
удаление станет ретроспективной миграцией; в бэкапах продолжит лежать то, что владелец
считает удалённым, а процедура ответа на запрос субъекта ПДн остаётся неописанной.
