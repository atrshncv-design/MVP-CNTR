# ADR 0008: WAL/history offsite с retention и обязательным crypt

**Tier:** T2 — data-safety, reversal = потеря RPO/RTO и несоответствие 152-ФЗ
**Date:** 2026-08-28
**Status:** accepted

## Title
Непрерывная архивация WAL + .history на отдельный том, retention из env и offsite только через rclone crypt

## Context
На старте M0 бэкапы делались вручную, WAL не архивировался — гибель primary между суточными дампами означала потерю всех транзакций, а гибель хоста — потерю и бэкапов вместе с данными. Заказчик — госструктура с ПДн расширенного набора; выбор внешнего S3/минio-хранилища ещё не сделан, но отправлять незашифрованные дампы/сегменты за периметр нельзя. Требовались RPO ≤ 5 мин, RTO ≤ 1 ч, при этом offsite не должен стать каналом утечки, а retention не должна стать сюрпризом на проде.

## Decision
- WAL на отдельный том: `archive_command` с атомарной записью + `archive_timeout = 60s` (RPO ≤ 5 мин доказывается, а не декларируется); в архив попадают завершённые сегменты WAL и `.history` (timeline history) — без hidden/temp/partial файлов.
- Retention управляется из env (`BACKUP_KEEP`, `WAL retention`), а не хардкодом; возраст последнего успешного снапшота и свежесть WAL-маркера — отдельные метрики для алертера.
- Offsite двухуровневый: ежедневная копия base-backup через `backup.sh` + непрерывная синхронизация WAL-архива sidecar-контейнером. Транспорт — rclone remote, но перед любой отправкой проверяется `type = crypt`; `no_data_encryption = true` и plain remote → `fail` без копирования данных. Незаданный таргет → предупреждение алертера (жёлтый), а не тихая деградация.
- Скрипты sidecar запечены в образ, данные — только на volume/mount (см. ADR 0009).

## Consequences
**Положительные:** потеря ограничена минутами независимо от времени суток; offsite переживает гибель физического сервера; шифрование на стороне клиента делает выбор провайдера (S3 заказчика) ортогональным безопасности — можно менять backend без смены контракта; retention прозрачна для эксплуатации и тестируется.

**Отрицательные / цена:** без настроенного crypt-remote offsite фактически не работает — прод остаётся «жёлтым» до действий оператора, это осознанное трение; sidecar добавляет один процесс и один healthcheck, требующий мониторинга; неправильный `type=crypt` блокирует отправку даже при доступном бакете; хранение `.history` увеличивает объём, но необходимо для PITR через переключения timeline.

**Что отвергли и почему:**
- *Только суточные pg_basebackup без WAL* — отвергнуто: RPO = до 24 ч, не проходит требование «≤ 5 мин» и не переживает транзакции между бэкапами.
- *Отправка WAL/base на plain rclone remote с серверным шифрованием* — отвергнуто: для ПДн offsite без client-side encryption недопустим; серверное шифрование оставляет данные читаемыми оператору хранилища.
- *Хранение WAL в том же томе, что и PGDATA* — отвергнуто: переполнение диска PGDATA убивает primary; отдельный том изолирует архив и делает мониторинг независимым.
- *Retention хардкодом в скрипте* — отвергнуто: политика хранения — решение эксплуатации/заказчика, а не сборки; хардкод гарантирует расхождение с реальными требованиями.
