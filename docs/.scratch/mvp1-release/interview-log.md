## Решения (лог)

| # | Вопрос | Решение (verbatim) |
|---|--------|--------------------|
| 1 | Сформулируй MVP1 одним проверяемым сценарием | «Любой потенциальный участник центра может зарегистрироваться; в его ЛК весь визуал работает и привязан к коду. Реализован опросник УГТ проектов — универсальный опросник для автоматической оценки УГТ» |
| 2 | Что значит «универсальный опросник» (существующий визард уже реализован) | **(a) + (c)**: существующий визард — ядро, закрывает требование; «универсальность» = оценка УГТ как самостоятельный инструмент, доступный из любого ЛК, + повторная переоценка из карточки проекта |
| 3 | Кто может проводить оценку УГТ; можно ли переоценить созданный проект | **ПОПРАВКА пользователя**: экспресс-оценка УГТ доступна ЛЮБОМУ пользователю (учёный, ГК, МТК и др.) — любой может «закинуть свой проект на платформу» и получить экспресс-оценку УГТ. Если проект уже создан — переоценить НЕЛЬЗЯ: доработка только через прохождение уровней УГТ и фиксацию документов (пример: проект на УГТ3 → нельзя переоценить → добавить документы, необходимые для УГТ4 → получить статус УГТ4). |
| 4 | Механика «повышения УГТ» проекта документами (УГТ3 → УГТ4): кто/что подтверждает переход | **Формат MVP (предложение пользователя)**: при внесении документов система даёт только ПОТЕНЦИАЛЬНУЮ (предварительную) оценку — анализирует документы на соответствие требованиям УГТ центра и ГОСТам → «документы приняты, предварительная оценка успешна / не успешна»; при неуспехе сразу перечисляет, чего не хватает. Финальную ВЕРИФИКАЦИЮ заявки на повышение УГТ выполняет МЕНЕДЖЕР ЦЕНТРА (не эксперт УГТ). |
| 5 | Откуда берётся база для потенциальной оценки документов («требования УГТ центра + ГОСТы») | **Пока оценка ведётся СУГУБО НА ГОСТАХ** (RAG: ГОСТ Р 58048-2017 + 71726/71727/71728/71729-2024 + 56645.x + 57194.x + 57193-2025 — уже загружены в seed_gost). Отдельные документы центра — ПОЗЖЕ, не в MVP. Т.е. LLM сверяет загруженные документы с критериями УГТ из ГОСТов и отвечает «принято / чего не хватает». |
| 6 | Жизненный цикл заявки на повышение УГТ (статусы, повторные попытки, история) | **(a) Лента статусов + повторяемая оценка**: «Документы загружены» → «Предварительная оценка: успешно / не хватает (список)» → «На верификации у менеджера» → «УГТ повышен» / «Отклонено (с причиной)». При неуспешной предварительной оценке пользователь видит список недостающего, дозагружает документы и перезапускает оценку без ограничений; менеджеру уходит только успешная версия. Вся история — в карточке проекта. |
| 7 | Куда сохраняется экспресс-оценка; кто может создавать проекты; кто присваивает официальный УГТ | **(a) + правка пользователя**: экспресс-оценка создаёт проект-ЧЕРНОВИК в ЛК пользователя. Порядок: пользователь заполняет карточку проекта → получает ПРЕДВАРИТЕЛЬНУЮ оценку УГТ → черновик верифицирует МЕНЕДЖЕР ЦЕНТРА: апрувнует карточку (проверяет соответствие действительности) и ПРИСВАИВАЕТ официальный УГТ. Создать проект (черновик) через экспресс-оценку может ЛЮБОЙ пользователь (учёный, ГК, МТК и др.). |
| 8 | ЛК менеджера ЦНТР с двумя очередями верификации | **(a) Две отдельные очереди**: вкладка «Новые проекты» (карточка + радар УГТ + предварительная оценка → «Подтвердить и присвоить УГТ N» / «Отклонить с причиной») и вкладка «Заявки на повышение УГТ» (документы + заключение системы → «Подтвердить уровень» / «Отклонить с причиной»). При отклонении владелец видит причину, исправляет и подаёт снова; история попыток сохраняется. |
| 9 | Что остаётся эксперту УГТ (в спеке — верификация чек-листов/уровней, акт верификации) | **ПОПРАВКА пользователя**: эксперт УГТ по своей сути — РЕГУЛИРУЮЩАЯ ОРГАНИЗАЦИЯ, которая может вносить на платформу документ о подтверждении УГТ проекта. Для MVP это ЛИШНЯЯ функция — РОЛЬ УБИРАЕМ (как именно — уточняется в вопросе 10). ВАЖНО: это меняет ранее зафиксированное «все 9 ЛК рабочие без моков» → остаётся 8 ролей (или роль остаётся пустой — зависит от решения по вопросу 10). |
| 10 | Как убираем роль эксперта УГТ (решение по №9) | **ПОПРАВКА пользователя**: роль НЕ убираем — ОСТАВЛЯЕМ, но переименовываем «Эксперт УГТ» → **«Регулирующая организация»**. Ролей по-прежнему 9, «все ЛК рабочие» остаётся в силе. Что именно в ЛК этой роли в MVP — уточняется в вопросе 11. |
| 11 | Что в ЛК роли «Регулирующая организация» в MVP | **Решение пользователя**: регулирующая организация РЕГИСТРИРУЕТСЯ на платформе, но доступ к добавлению ВЕРИФИЦИРУЮЩИХ ДОКУМЕНТОВ (документ о подтверждении УГТ проекта) получает только ПОСЛЕ присоединения к карточке конкретного проекта по его УНИКАЛЬНОМУ ТОКЕНУ (join-токен TZ-XXXXXX — механика уже реализована в membership.py: приоритетный шаринг → авто-вступление, иначе заявка + одобрение). ЛК роли = список присоединённых по токену проектов + добавление документов подтверждения УГТ к ним. НЕ решено: эффект документа на УГТ-уровень проекта (вопрос 12). |
| 12 | Эффект документа подтверждения УГТ от регулирующей организации на проект | **(b) + обоснование пользователя**: документ — ПОДТВЕРЖДАЮЩИЙ МАТЕРИАЛ для менеджера: попадает в очередь менеджера (№8) как доказательство, финальное решение за менеджером (единый авторитет по УГТ). Роль нужна: без документов сторонних организаций верификация УГТ невозможна. Роль НЕ монопольна: другие участники могут сами получить документ у организации и загрузить его на платформу — главное, чтобы документ оказался на платформе. |
| 13 | Публикация проекта: после апрува менеджером — где и для кого виден проект | **(c) Гибрид**: общий реестр проектов — ВСЕ роли видят карточки с УГТ-уровнем и радаром после апрува менеджера; отдельный «реестр технологий УГТ 7+» сохраняется «как сегодня» (инвестор — read-only с фильтрами, серийный производитель — заявка на лицензию). Черновики и отклонённые — только владелец и менеджер. |
| 14 | Как проект попадает в реестр технологий УГТ 7+ | **(a) Автоматически** при подтверждении менеджером УГТ ≥ 7: карточка сразу появляется в реестре технологий. Реестр технологий = реестр проектов с фильтром «УГТ 7+» (одна карточка, одни данные, без новой сущности). ДОПОЛНЕНИЕ пользователя: формируются ДВА ПАРАЛЛЕЛЬНЫХ СПИСКА проектов — общая витрина (все проекты) и список, отсортированный по уровням УГТ; в обоих списках возможна фильтрация по доп. параметрам (область технологии, бюджет и др.). |

| 15 | Кто подаёт заявку на повышение УГТ (варианты: владелец / участники / менеджер) | **Автоматическое формирование (решение пользователя)**: заявка формируется АВТОМАТИЧЕСКИ при наполнении карточки проекта необходимыми документами текущего этапа. Не важно, кто залил последний нужный документ (владелец или любой участник) — после загрузки последнего документа клиент получает ПРЕДВАРИТЕЛЬНУЮ оценку, а МЕНЕДЖЕР получает УВЕДОМЛЕНИЕ о заявке. Т.е. триггер заявки — полнота комплекта документов, а не действие конкретного пользователя. |
| 16 | Откуда берётся словарь «необходимых документов текущего этапа» (триггер автозаявки) | **Формат MVP (модифицированный (b))**: списки необходимых документов для каждого этапа повышения УГТ формирует LLM по ГОСТам (RAG) ОДИН РАЗ (не в рантайме, не с нуля при каждой заявке). Сформированные списки пользователь ВЕРИФИЦИРУЕТ с методологом центра → верифицированный список используется постоянно как детерминированный триггер автозаявки (№15). |
| 17 | Модель перехода по уровням УГТ («этап» в списках документов из №16) | **(a) Строго по одному уровню (N → N+1)**: этап = конкретный переход (УГТ3 → УГТ4); проект видит документы только для следующего уровня; автозаявка (№15) срабатывает по полноте комплекта именно этого этапа; после апрува менеджера открывается следующий этап. Всего 8 этапов (1→2 … 8→9). Перепрыгивать уровни нельзя — только последовательное прохождение уровней (как в №3). |
| 18 | Демо-маршрут на приёмке 31.08 под новые механики | **(a) Демо перестраивается вокруг нового флоу верификации**: регистрация любой организации → экспресс-оценка УГТ (опросник) → черновик с предварительным УГТ → ЛК менеджера: апрув карточки, присвоение официального УГТ → проект в общем реестре (+ реестр технологий при УГТ 7+) → доработка документами: автозаявка → предварительная оценка → верификация менеджером → УГТ повышен. Генерация документов и AI-ассистент остаются в продукте, но в демо — бонус-шаги, если остаётся время. Подтверждённые куски (опросник, реестры, join-токен) не выбрасываются — становятся шагами нового маршрута. |
| 19 | **Критерии приёмки «сданного» MVP1 31.08** | **(a) Сценарий «нового флоу» проходит целиком на живых данных** — чек-лист приёмки: (1) регистрация любой из 9 ролей; (2) экспресс-оценка УГТ из ЛК → черновик с предварительным УГТ; (3) ЛК менеджера: апрув карточки → официальный УГТ; (4) проект виден в общем реестре (+ реестр технологий при УГТ 7+); (5) загрузка документов → автозаявка → предварительная оценка → верификация менеджером → УГТ повышен; (6) регулирующая организация присоединяется по токену и добавляет документ. Плюс: все 9 ЛК рабочие без моков, тесты зелёные. = демо-маршрут №18 + регресс прежнего QA (опросник, join-токен, реестры) — одно проверяемое целое. |
