# Технические требования к серверу — платформа «Технозрелость»

Одна виртуальная машина для пилотного промышленного контура. Всё приложение разворачивается
контейнерами (Docker Compose), отдельных физических серверов не требуется. Если к проекту
предъявляется требование отечественного ПО — сначала см. `ИМПОРТОЗАМЕЩЕНИЕ.md`, пункт про ОС.

## 1. Операционная система

| Требование | Почему |
|---|---|
| Ubuntu Server LTS 22.04 или новее (64-bit) — базовый вариант | Дистрибутив с лучшей документацией по Docker; все инструкции по деплою написаны под него |
| При требовании импортозамещения — Astra Linux SE или РЕД ОС | Совместимость с Docker и сборкой образов необходимо предварительно проверить на стенде (см. `ИМПОРТОЗАМЕЩЕНИЕ.md`) |

## 2. Контейнеризация

| Требование | Почему |
|---|---|
| Docker Engine ≥ 24 из официального репозитория docker.com | Свежая стабильная ветка; репозиторий docker.com даёт своевременные обновления безопасности |
| Плагин Compose v2 (пакет docker-compose-plugin) | Наш стек описан одним compose-файлом формата compose-spec; используется `deploy.replicas` (2 реплики API) и healthchecks — это возможности современного Compose v2 |
| Права пользователя на управление Docker (группа `docker` или sudo) | Деплой выполняется командой `./deploy.sh` на самом сервере, без внешних панелей |

## 3. Ресурсы

**CPU: 4 vCPU минимум, 8 vCPU рекомендуется.** Пики — при деплое: сборка образов (Next.js, FastAPI)
идёт прямо на сервере; антивирус сканирует загрузки файлов.

**RAM: 12 ГБ минимум, 16 ГБ рекомендуется** (сумма сервисов ~10,5 ГБ + ОС и кэши):

| Сервис | RAM | Почему |
|---|---|---|
| PostgreSQL Primary (pgvector/pg16) | 2 ГБ | Единственная точка записи всех транзакций; буферы должны сидеть в памяти |
| PostgreSQL Replica | 2 ГБ | Горячая копия того же объёма данных — читает реестры, снимает нагрузку с Primary |
| ClamAV | 2 ГБ | Антивирус самый прожорливый: базы сигнатур целиком в памяти, пики до ~3 ГБ при обновлении |
| MinIO (файлы проектов) | 1 ГБ | Хранит загруженные документы НИОКР; память уходит на буферизацию |
| Backend FastAPI × 2 | 2 × 0,5 ГБ | Две stateless-реплики за балансировщиком |
| Frontend Next.js | 1 ГБ | SSR-рендер кабинетов; ещё ~2 ГБ кратковременно съедает сборка при деплое |
| nginx | 0,1 ГБ | Точка входа TLS, балансировка API |
| Redis | 0,25 ГБ | Зарезервирован (кэш/очереди) |
| Prometheus + Grafana | 1,5 ГБ | Метрики и дашборды; Grafana наружу не публикуется (доступ по SSH-туннелю) |

**Диск: 500 ГБ SSD/NVMe.** PostgreSQL и сборка образов чувствительны к скорости диска,
HDD не подходит:

| Том | Размер | Почему |
|---|---|---|
| Система + Docker (образы, кэш сборки) | 60 ГБ | Образы всех сервисов и слои сборки при каждом деплое |
| Данные PostgreSQL Primary | 50 ГБ | База платформы; запас на рост реестров и документов |
| Данные PostgreSQL Replica | 50 ГБ | Полная копия Primary |
| MinIO (файлы) | 100 ГБ | Загружаемые документы проектов — основной растущий объём |
| Резервные копии БД | 150 ГБ | Ежедневные дампы, хранение 14 копий + запас |
| WAL-архив (отдельный том) | 50 ГБ | Непрерывный архив журналов: потеря данных при аварии ≤ 5 минут |
| Метрики Prometheus | 30 ГБ | История телеметрии |
| Базы сигнатур ClamAV | 5 ГБ | Растут с каждым обновлением |

## 4. Сеть

| Требование | Почему |
|---|---|
| Входящий TCP 80 и 443 до сервера | 443 — сайт и API по TLS; 80 — автоматическое получение сертификата Let's Encrypt и редирект на HTTPS |
| Статичный публичный IP | Привязка домена и выпуск сертификата |
| Исходящий HTTPS (443) без ограничений | Три обязательных направления: LLM-API (AI-функции), CDN FreshClam (обновление антивируса), реестры пакетов apt/pip/npm и Docker Hub (сборка и обновление образов) |
| NTP-синхронизация времени (udp/123) | TLS-сертификаты и JWT-токены ломаются при расхождении часов; расписание бэкапов тоже считает время |
| Работающий DNS-резолвер | Резолвинг нужен и контейнерам внутри стека, и исходящим вызовам |

## 5. Доступы

| Требование | Почему |
|---|---|
| SSH-доступ для администратора платформы (по ключам, вход под root по паролю отключить) | Запуск деплоя, миграций, чтение логов; ключи вместо пароля — базовая гигиена |
| Отдельный SSH-доступ для туннеля к Grafana | Панель мониторинга намеренно не опубликована в интернет; попасть в неё можно только туннелем `ssh -L 3001:grafana:3000 …` (команда — в README инфры) |
| Передача доступа через защищённый канал (менеджер паролей, одноразовые ссылки) | Значения секретов нельзя отправлять почтой/мессенджерами открытым текстом |

## 6. Что предоставляет заказчик

| Пункт | Детали | Почему |
|---|---|---|
| Домен и DNS | A-запись домена на IP сервера до деплоя | Сертификат и NEXTAUTH_URL завязаны на доменное имя |
| Offsite-таргет для бэкапов | Любое хранилище с поддержкой rclone (S3-совместимое облако, FTP/SFTP и т. п.) + учётные данные | Копия бэкапов вне сервера: гибель машины не должна уничтожать бэкапы вместе с данными |
| Значения секретов | Заполняется `.env.production` на сервере (файл в .gitignore, значения никуда не коммитятся) | Платформа не стартует без них; значения знает только заказчик |

Полный перечень имён переменных из `.env.production.example` (значения генерирует/хранит
заказчик; `JWT_SECRET` и `NEXTAUTH_SECRET` могут быть оставлены пустыми — их сгенерирует
`./deploy.sh` при первом запуске; `BACKUP_AT`, `BACKUP_FRESHNESS_MARKER`,
`BACKUP_OFFSITE_MARKER` — служебные дефолты, менять не требуется):

```
POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
REPL_USER, REPL_PASSWORD, REPL_SLOT
CORS_ORIGINS
LLM_API_BASE, LLM_MODEL, LLM_API_KEY          # без ключа платформа работает, кроме AI-функций
MINIO_ACCESS_KEY, MINIO_SECRET_KEY, MINIO_BUCKET
NEXTAUTH_URL                                   # https://<домен заказчика>
GRAFANA_ADMIN_USER, GRAFANA_ADMIN_PASSWORD    # обязателен нестандартный пароль
BACKUP_BEFORE_MIGRATIONS                       # бэкап перед миграциями деплоя
BACKUP_AT                                      # время ежедневного автозапуска backup.sh (ЧЧ:ММ)
BACKUP_KEEP                                    # сколько копий хранить локально
BACKUP_FRESHNESS_MARKER                        # файл-маркер свежести для алертера
BACKUP_MAX_AGE_HOURS                           # порог свежести бэкапа в часах
BACKUP_OFFSITE_REMOTE                          # rclone-таргет offsite-копии; пусто = выключено
BACKUP_OFFSITE_MARKER                          # файл-маркер статуса offsite
```

Планируются (появятся вместе с Telegram-алертером, таск 05 прогона — пока в примере их нет):
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

## 7. Бэкапы и снапшоты заказчика

| Ожидание | Почему |
|---|---|
| Платформа сама делает ежедневный дамп БД + непрерывный WAL-архив и копирует его на offsite-таргет | Восстановление на любую точку с потерей ≤ 5 минут — свойство платформы, не ручной работы |
| Снапшоты гипервизора НЕ заменяют бэкапы приложения | Снапшот снимает «замороженное» состояние машины целиком, включая работающую БД, и живёт на том же железе; это разные уровни защиты |
| Просьба к заказчику: ежедневный снапшот VM, хранение на другом физическом носителе/хосте, тестовое восстановление раз в квартал | Защита от выхода из строя самого гипервизора; непроверенный снапшот — не бэкап |
