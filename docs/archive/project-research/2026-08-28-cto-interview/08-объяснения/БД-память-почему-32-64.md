# БД память — почему 32/64 ГБ и альтернатива

## Почему БД жрет RAM
PostgreSQL RAM = shared_buffers (25% RAM) + work_mem * connections + cache:
- shared_buffers 8 ГБ (32 ГБ хост) кэширует hot карточки `nioktr_cards` + индексы GIN/trgm `P-05` + vector `ivfflat` (6 ГБ на 1М)
- work_mem 64МБ *100 connections = 6.4 ГБ
- OS cache 10 ГБ для seq scan `P-06`

На 16k и 714 RPS 5К — хватает 16 ГБ PG (8 shared). На 1М + 1428 RPS 10К — 16 ГБ даст 90% cache miss -> p95 2с.

## 84->140 ГБ — это не только БД
84 ГБ 5К = App 20 (backend 12+frontend 8) + DB 48 (32+16) + MinIO 16 + Redis 4
140 ГБ 1М = App 28 + DB 96 (64+32) + MinIO 16

DB 32->64 — не вся прибавка, App тоже растет (больше RPS).

## Альтернатива без 64 ГБ БД
Можно оставить PG 16/32, но:
- Партиционирование `nioktr_cards` по sector (меньше кэша)
- `read Replica` `database.py:21` разгрузит 50% RPS
- `Redis` кэш `P-09` справочников
- `keyset` пагинация `P-08` вместо `count` `nioktr.py:76`

Тогда 1М на 16/32 PG выдержит p95 500мс, но нужен `pgbouncer` + `GIN`. 64 ГБ — запас на рост без шардирования, не обязательно сейчас.

Вывод: до 500k — 16 ГБ PG хватит, 64 ГБ — max на 1М без оптимизации. Для 5К бери 16/32, не 32/64.
