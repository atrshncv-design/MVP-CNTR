# Монолит vs большие реестры — выдержит?

## Твои реестры
МТК/ВУЗы/проекты/технологии/УГТ — `nioktr_cards` 16k сейчас, будет 100k-500k с хаотичным ingest `04-` + `P-05`.

## Монолит выдержит до
- 100k карточек: с индексами `P-05` `trgm GIN` `ILIKE`, `GIN` JSONB `nioktr_types`, Hash `ogrn`, B-Tree `is_ai_area` `0027` + пагинация `P-07` `limit 50` + `keyset` `P-08` — монолит FastAPI `app/api/v1/nioktr.py:56` 930 RPS держит на 8/32.
- 500k: нужен `pgbouncer` + `Redis` кэш `P-09` + `LATERAL` count `P-06` (сейчас `SELECT count` на каждую организацию O(N) `nioktr.py:76`)

## Когда не выдержит
- 1M+ + 5К RPS + RAG vector search без `ivfflat` `0028` — тогда шардировать: вынести `RAG` + `read Replica` `database.py:21` уже есть.
- Разнообразие — не объём, а `JOIN` МТК+ВУЗ+проект — монолит с `asyncpg` справится, микросервисы добавят хопы.

Вывод: до 500k монолит с индексами/пагинацией выдержит, ты не ошибаешься в риске, но решение — индексы, не микросервисы (как 13-).
