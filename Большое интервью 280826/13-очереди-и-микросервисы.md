# 13 — Очереди и микросервисы (ответ CTO на Q16)

## Где обязательны очереди (13 hotspots, 8 критичны на 5К)
| # | Файл:строки | Риск при 2+ юзерах одновременно | Решение |
|---|---|---|---|
| R1 | `stages.py:175` `_next_version` `files.py:57` | 2 загрузки `title` → дубль `version=6` | `pg_advisory_xact_lock(project_id)` + UNIQUE |
| R2 | `stages.py:203` `_trigger_application` | 2 последних дока параллельно → дубль `PromotionRequest` | advisory lock + partial UNIQUE |
| R3 | `stages.py:320` `_evaluate` внутри транзакции 60с | Держит пул 60с → 503 | Redis queue `llm-eval` + outbox, 202 Accepted |
| R4 | `file_storage.py:200` put до commit | Орфан MinIO при rollback | DB-first + compensation queue |
| R5 | `achievements.py:141` `_award` NULL ломает UNIQUE | Дубль медалей 500 | `ON CONFLICT DO NOTHING` + outbox worker |
| R6 | `manager.py:241` `decide_promotion` | 2 менеджера Approve → N+2 | `SELECT ... FOR UPDATE` |
| R8 | `news_scheduler.py:20` fan-out 5К | 5К INSERT в одной транзакции минуты | `INSERT SELECT` одним SQL + Redis PubSub |
| R9 | `invites.py:132` used_count | 20 accept при max 10 | `UPDATE ... WHERE used_count<max RETURNING` |
| R11 | `auth_throttle.py:18` dict per process | 2 реплики → лимит 20/60 | Redis `INCR EXPIRE 60` |
| R12 | `main.py:56` scheduler ×2 | 2 лупа 60с | Вынести в 1 контейнер scheduler |

Правило: `advisory lock + outbox + Redis` покрывает 90% без Kafka.

## Что выносить из монолита
- **Оставить в монолите до 10К:** RAG/LLM (только воркер queue), document_generator (queue), achievements (outbox), file_storage (presigned URL), notifications (воркер, не сервис). Причина: solo-CTO, транзакционная консистентность, 1 репо.
- **Вынести обязательно до 5К:** `scheduler` → 1 контейнер (как backup-timer), `auth_throttle` → Redis.
- **После 10К и найма:** notification+realtime (cross-replica), RAG (ANN + GPU). `scheduler` самый дешёвый вынос — 1 файл.

До 5К — добавить 5 патчей (advisory lock 3 строки, Redis throttle, scheduler контейнер, compensation, llm queue) без распила.
